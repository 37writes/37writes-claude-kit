# 기획 강화와 멀티 에이전트 배치 개선

## 목표
kit의 목적(기획 강화, 멀티 에이전트 사용)에 맞게 harness·plan·check·init 규칙을 고친다.
기획은 구현 전에 다른 모델이 반박하고, 워커 배치는 줄 수가 아니라 위험도·불확실성·분리 가능성으로 정하고, 승인을 두 번 묻거나 빠뜨리지 않고, 검증자는 구현자 검사 재실행 외에 스스로 고른 실패 시나리오를 확인한다.

## 배경 (현재 문서에서 확인한 것)
- 기획 검토 규칙이 없다. plan 3단계 "설계 점검"은 작성자 혼자 한다.
- harness 1단계: T0 예가 "20줄 미만 파일 하나 수정", "워커를 띄울지는 변경 규모로". 줄 수·파일 수가 배치를 정한다. 원인 불명 조사, 병렬 구현, 기획 반박 같은 배치 구분이 없다.
- plan 5-3 "바로 구현을 시작할지 묻는다": 사용자가 구현까지 맡겨도 다시 묻는다.
- check "점검 단계에서는 코드를 수정하지 않는다 … 어떤 것을 고칠지 묻는다": harness 검증 단계에서 쓰면 이미 승인된 구현의 결함까지 다시 승인받게 된다.
- push 등급 불일치: harness·init·CLAUDE.md는 "배포가 되는 push"가 T2, plan 99줄은 "push"가 T2, design 94줄은 "배포·push는 T2".
- harness 5단계 검증은 재실행·범위·시크릿·재계산뿐이다. 검증자가 스스로 실패 시나리오를 고르는 규칙이 없다.
- harness T2 "실행 전 계획 승인"과 "적용 전 미리보기"가 각각 무엇을 확인하는지, 언제 다시 승인받는지 적혀 있지 않다.

## 설계

### 1. 다른 모델의 기획 반박 (harness 2단계, plan)
- **언제**: 불확실성이 높거나(확인 안 한 가정, 설계 갈림길, 원인 불명) 영향이 큰(T2, 여러 프로젝트에 퍼지는 규칙·훅) 기획. 작고 명확한 T1은 하지 않는다.
- **누가**: 작성자와 **다른 실제 모델**. Claude가 썼으면 Orca `worker-start --agent codex|antigravity` 탭. 같은 모델에 역할 이름만 바꾼 검토는 충족이 아니다. 모델은 `launch.effective` 또는 워커가 보고한 실행 모델로 확인하고, 확인 못 하면 "미확인"으로 적고 완료라고 하지 않는다.
- **무엇을**: (1) 사용자 문제를 정말 해결하는가 (2) 더 작은 해법 (3) 확인하지 않은 가정 (4) 완료 기준은 통과해도 실사용에서 깨지는 반례. 결과는 **중요한 반례 최대 3개 + 각각 확인 방법**.
- **구현 전 차단**: 반박 대상 기획은 반박과 수용/기각 기록이 끝나기 전에 구현하지 않는다. 다른 모델을 쓸 수 없으면 구현을 멈추고 사용자에게 예외로 진행할지 묻는다. 예외로 진행하면 기획서에 "다른 모델 반박 미완료(사유)"를 남긴다. 반박 대상이 아닌 작업은 해당 없음.
- **반영**: 작성자는 기획서 "기획 반박" 섹션에 검토자(agent·model·ID), 반례별 수용/기각 + 이유를 적고 계획을 고친다. 사용자 결정이 필요한 것은 이 뒤에 묻는다 (사용자에게는 반박을 거친 계획을 보인다).
- plan 스킬: 3단계 설계 점검 뒤에 "기획 반박" 단계를 두고 harness 2단계 기준을 참조한다. 기획서 양식에 "기획 반박" 섹션.

### 2. 위험도·불확실성·분리 가능성으로 배치 (harness 1·3단계, orca_context.py)
- 등급(T0~T2)은 영향 범위 그대로. 따로 **불확실성**(원인·해법이 분명한가)과 **분리 가능성**(서로 안 겹치는 파일·모듈로 나뉘는가)을 본다. 줄 수·파일 수는 근거가 아니다 (T0 예의 "20줄 미만"을 뺀다).
- 배치 표:

  | 상황 | 배치 |
  |---|---|
  | 작고 원인·해법이 분명 | 지휘 세션이 직접 (T1이면 검증은 다른 워커) |
  | 작아도 원인이 불명 | 읽기 전용 조사 워커 → 결과로 다시 분류 |
  | 겹치지 않는 모듈 여러 개 | 병렬 Coder(각자 하위 worktree) + 통합 검증 |
  | 설계가 불확실하거나 영향이 큼 | 다른 모델 기획 반박 → 구현 → 독립 검증 |

- 필요한 역할만 띄운다. 같은 worktree의 차례 역할은 탭, 동시에 파일을 고칠 때만 하위 worktree (기존 3단계 유지).
- orca_context.py 안내문의 "변경 규모상 워커가 필요하면" → "위험도·불확실성·분리 가능성으로 배치를 정하고(harness 1단계)".

### 3. 승인 규칙 (harness 새 소절, plan 5단계, check, init, design)
- **계획 승인(실행 전)**: 무엇을 어디까지 할지 승인. 승인(또는 처음 요청)에 구현이 들어 있으면 "바로 구현할까요?"를 다시 묻지 않는다. 기획만 요청했으면 구현하지 않고 멈춘다.
- **미리보기(적용 전, T2)**: 실제로 바뀌는 것이 승인한 범위와 같은지 확인하는 단계. 계획 승인을 대신하지 않는다. harness 6단계: 사용자가 대상을 정해 적용까지 승인했고 미리보기가 그 범위와 같으면 다시 묻지 않고 적용한다. 구현만 승인했거나 미리보기에 예상 밖 변경이 있으면 미리보기를 보여 주고 적용 승인을 받는다. guard의 명령 실행 확인 창은 대화 승인과 별개로 그대로 둔다.
- **다시 승인받는 경우**: 승인 범위 밖 파일·시스템, 새 외부 영향(배포, 배포가 되는 push, 삭제, 권한·시크릿), 미리보기에 예상 밖 변경. **다시 묻지 않는 경우**: 승인된 구현 안에서 검증이 찾은 결함의 수정·재검증.
- **점검 요청**: 사용자가 따로 "점검해줘"라고 하면 check대로 보고 먼저, 수정은 승인 후. harness 검증 단계에서 check를 쓰면 결과는 지휘 세션이 받고, 범위 안 결함은 Coder에게 다시 맡긴다 (사용자 재승인 없음).
- **push**: T2는 "배포가 되는 push". 일반 push는 프로필 push 줄(`배포 아님`이면 커밋 승인이 push 승인), 줄이 없으면 묻는다. 강제·삭제 push는 항상 따로 확인. guard 동작은 바꾸지 않는다. plan 99줄, design 94줄을 이 표현으로 맞춘다. init은 초기화 중에는 push하지 않는다(명시적 예외, 원격 저장소 생성만 확인). 이후 push는 프로필 push 줄을 따른다고 서문과 6단계를 고친다.

### 4. 검증자의 독립 실패 시나리오 (harness 5단계, check)
- 재실행·범위·시크릿 검사에 더해, Validator는 기획서의 완료 기준에서 **직접 1~3개의 중요한 실패·경계 시나리오**를 골라 확인한다 (Coder 보고에 나온 시나리오를 그대로 쓰지 않는다).
- 기존 테스트가 그 시나리오를 덮으면 재사용한다. 구현을 그대로 베낀 테스트를 새로 만들게 하지 않는다. 문서 변경이면 실제 실행(새 세션에서 스킬 적용)이나 문서 대조로 확인한다.
- 보고에 시나리오별 **선택 이유, 재현 절차·명령, 실제 결과, 미검증 사항**.

## 결정 & 이유
- 새 스킬을 만들지 않고 harness에 규칙을 모은다 → plan·check·init은 harness를 참조. 규칙이 한곳에 있어야 문서끼리 어긋나지 않는다.
- 기획 반박은 조건부 → 모든 T1에 붙이면 작은 작업이 느려진다 (사용자 요청: 기계적으로 모든 역할을 띄우지 않기).
- guard는 그대로 → 사용자가 push 보호 범위 변경을 요청하지 않았다.

## 엣지 케이스 & 리스크
- 다른 모델 워커가 없는 환경(Orca·Codex 없음): 서브에이전트는 같은 모델이므로 반박 완료가 아니다. 반박 대상이면 구현을 멈추고 사용자에게 예외 여부를 묻는다 (설계 1).
- 문서가 길어져 harness 로드 비용이 커진다 → 표 하나 + 짧은 소절로, 중복 설명 없이.
- plan 기획서 양식의 검증 단계 예시가 재실행만 적혀 있어 복제된다 → 독립 시나리오를 넣는다. harness 서문의 "사용자가 Plan Reviewer"는 다른 모델 반박자와 사용자 승인자를 구분한다.
- 기존 세션은 예전 스킬을 그대로 들고 있다 → 검증은 worktree를 `--plugin-dir`로 로드한 새 세션(`command claude`, alias 우회)이나 worktree 원본 읽기로.

## 완료 기준
- 반박 대상인데 다른 모델을 쓸 수 없는 상황을 준 새 세션은 구현을 시작하지 않고 예외 여부를 묻는다.
- T2에서 "구현만 승인"이면 미리보기 뒤 적용 승인을 받고, "대상을 정해 적용까지 승인" + 미리보기 일치면 다시 묻지 않는다. guard 확인 창은 그대로 뜬다.
- init의 push 지시가 프로필 규칙과 충돌하지 않는다 (초기화 중 push 없음이 명시적 예외).
- worktree 플러그인을 로드한 새 세션에서: 기획만 요청하면 기획서만 쓰고 구현하지 않으며, 구현까지 요청하면 "바로 구현할까요?"를 다시 묻지 않는다. 따로 "점검해줘"라고 하면 수정 없이 보고한다.
- harness를 읽은 세션이 줄 수가 아니라 불확실성·분리 가능성으로 배치를 설명한다. 불확실한 기획에는 다른 모델 반박을 요구한다.
- harness·plan·init·design·CLAUDE.md의 push 등급 표현이 같고(배포가 되는 push만 T2), guard 테스트 결과가 변경 전과 같다.
- Orca 안 세션 시작 안내가 새 배치 기준을 말하고, Orca 밖에서는 아무것도 출력하지 않는다.
