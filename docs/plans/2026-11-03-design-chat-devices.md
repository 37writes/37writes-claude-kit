# kit:design에 대화형 화면·기기 상황 매트릭스·레퍼런스 보드 추가

## 목표
사용자가 한 프로젝트에서 낸 디자인 요구를 kit:design의 공통 규칙으로 올린다. 어느 프로젝트에서든 다음 세 가지를 같은 방식으로 지키게 한다.
- 한 명의 디자이너가 만든 것 같은 통일감
- 주요 기기의 상황별 배치
- 여러 레퍼런스를 보고 방향을 고르는 절차

## 사용자 요구 (2026-11-03, 일반화)
- 디자인은 한 명의 디자이너가 작업한 것처럼 통일되고, 심플하고 명확해야 한다.
- 주요 기기의 상황별 배치를 반드시 고려한다. 폰 세로·가로, 키보드가 올라온 상태, 태블릿과 분할 화면, 노트북, 넓은 화면이 대상이다.
- 많은 레퍼런스를 확인해 여러 디자인 느낌을 비교할 수 있게 한다.
- 대화형(채팅) 화면에서 정한 것:
  - 기본 UI가 드러나지 않는 느낌으로 하고, 답의 형태는 질문에 따라 달라진다.
  - 답은 글만이 아니라 그래프·도형으로 빨리 이해시킨다.
  - 느리지 않다고 느끼게 하는 체감 속도 장치를 허용한다.
  - 모바일은 얇은 한 줄 바(☰ + 경로)를 쓴다.
  - 입력 영역이 화면을 차지하지 않게 한다. 키보드는 탭할 때만 올라온다.
  - 나중에 음성 대화를 붙여도 막히지 않게 한다.

## 범위
- 포함
  - `skills/design/SKILL.md`
  - `skills/design/references/` (새 참조 파일 포함)
  - `README.md`의 design 설명
  - 플러그인 버전
- 제외
  - 테마 색값과 CSS 자산 변경. 대화형 부품 CSS는 실제 프로젝트에서 검증한 뒤에 따로 다룬다.
  - 개별 프로젝트 파일 편집
  - 회사·서비스·고객사 이름. 공개 레포이므로 예시는 일반 도메인으로만 쓴다.

## 설계 (반박 반영)
1. **통일감 점검표** (`references/system.md` 공통 원칙 뒤에 "한 디자이너 점검" 절로 추가)
   - 역할별로 토큰 한 벌을 둔다(간격 단계, 글자 단계, 모서리, 선 두께, 아이콘 세트·굵기). 제목과 본문의 크기 차이나 반응형 밀도 차이는 허용한다.
   - 같은 역할에는 같은 부품을 쓴다. 상태 표현(로딩·빈 화면·오류)과 문구 어조는 화면마다 같다.
   - 강조색 규칙은 기존처럼 오류·성공·범례색을 지우라는 뜻이 아니다.
   - 새 화면은 기준 화면 옆에 놓고 같은 역할의 부품을 계산값으로 대조한다.
   - 프로젝트별 예외는 프로필에 이름과 이유를 적는다.
2. **기기·상황 행** (`references/ego-validation.md` "매트릭스와 실제 조작" 보강. 새 파일을 만들지 않는다)
   - 기존 폭·전환점 ±1px·모드·확대 검사는 그대로 두고, 상황 열을 더한다.
     - 기기: 폰 세로/가로, 태블릿, 분할 화면, 노트북, 넓은 화면
     - 상황: 키보드, 시트·패널, 메뉴, 긴 내용
   - 각 행에는 실제 폭×높이, 입력 방식, 남겨야 할 핵심 조작, 검증 수단을 적는다.
   - **변경 영향이 있는 행만 고른다.** 행마다 `적용 / 비해당(이유) / 미검증(이유)` 중 하나를 쓴다. 미검증을 비해당으로 지우지 않는다. 작은 수정은 영향받는 행만 본다.
   - 가상 키보드는 ego로 증명되지 않는다. 가용 높이 fixture는 시험 입력이라고 적는다.
3. **방향 선택 절차** (`SKILL.md` 1절 보강)
   - 세 경우를 구분한다: 기존 방향 유지(기본) / 새 방향 필요(프로필 없음) / 사용자가 재설계를 요청함. 새 화면 유형을 추가하는 것만으로 방향을 다시 고르지 않는다.
   - 새 방향이 필요하면 레퍼런스 보드를 만든다. 서로 다른 패턴을 주제별로 비교하고 "가져올 것 / 버릴 것"과 이유를 적는다. 사이트 수는 목표치(약 10곳)이고, 같은 패턴이 반복되면 멈추고 그 이유를 쓴다.
   - 시안은 2~4개로 하고 비교 축을 명시한다.
     - 공통 조건: 내용, 핵심 과업, 접근성, 부품 의미
     - 선택 축: 배치·밀도 그리고/또는 색·글꼴
     - 공유 fixture로 만든다.
   - 선택표에는 미관과 과업 성공을 별도 열로 둔다. 고른 결과는 프로필에 고정한다.
   - 개인정보:
     - 사용자 프로필에서 사용자 기록이 보이는 화면은 캡처하지 않는다.
     - 외부 AI에는 공개 일반 질문만 넣는다.
     - 제3자 캡처는 커밋하지 않는다.
4. **대화형 패턴** (S2b, 선택적 패턴. 작업 화면 유형의 하위)
   - `system.md` 화면 유형의 작업 항목에 "대화형은 작업의 하위 패턴, 상세는 `references/conversational.md`" 한 줄을 넣는다. 독립된 네 번째 유형으로 만들지 않는다.
   - **동작 계약(의무)**
     - 초안·커서·선택 상태를 보존한다. 편집 중에는 자동으로 접지 않는다. 자동 포커스는 하지 않는다.
     - 사용자가 위로 읽는 중이면 위치를 옮기지 않는다.
     - 근거·출처에 도달할 수 있고, 닫으면 원래 위치로 돌아간다.
     - 중지·재연결 때 중복이나 상태 역전이 없다.
     - 대기·미지원·실패를 구분해 보인다.
     - 진행 표시에는 실제 이벤트만 쓴다.
     - 조작 영역 44px과 확대 대응을 높이 상한보다 우선한다.
   - **배치 예시(프로젝트가 고른다)**: 한 줄 바, 접힌 입력창, 가독 폭 기반 패널/시트 전환, 음성 진입점, 높이 예산 수치. 수치는 "한 프로젝트에서 검증한 권장값"으로 쓴다.
   - 답의 구성은 질문에 따라 달라진다. 시각 블록은 의무가 아니다.
5. **버전**: 시스템 문서 계약 v1.0.0 → v1.1.0(규칙 추가). CSS 자산과 해시는 바뀌지 않는다. 문서 계약 버전과 vendoring한 자산 버전은 별개라는 점을 명시한다. 기존 프로젝트를 자동 이관하지 않는다. 플러그인 버전은 0.16.0 → 0.17.0(S2a), S2b에서 0.18.0.
6. **공개 필터**
   - 대상: `skills/design/`, README, 기획서와 보고서, 커밋 메시지 전체(`git log -p origin/main..HEAD`)
   - 확인 항목: 회사·고객·서비스명, 내부 URL·도메인, 계정 ID, 내부 문서 제목, 사내 질문 원문, 실제 데이터 수치, 이미지
   - 예시는 합성 사례만 쓴다. 매칭된 원문은 다시 출력하지 않는다.

## 결정 & 이유
- 대화형 패턴(4)은 비공개 프로젝트에서 시안과 독립 검증을 마친 뒤 일반화한다(S2b). 근거 없는 규칙을 먼저 넣지 않기 위해서다. 해제 증거는 그 프로젝트 검증 결과의 익명 요약이다.
- 1~3·5·6(통일감, 상황 행, 방향 절차, 버전, 필터)은 프로젝트와 무관하므로 지금 한다(S2a).
- 별도 `devices.md`는 만들지 않는다. 적용 범위와 생략 기준을 한 곳(ego-validation)에서만 정의해, 기존 폭 검사와 겹치지 않게 한다.
- 테마와 CSS는 바꾸지 않는다.
