# 자리 비움 1단계 기획 반박

**사건의 확인 창에는 효과가 있다.** 현재 `guard.py`에 사건과 같은 형태의 더미 명령을 JSON으로만 입력하니 `ask`가 나왔다. 기획서의 실측대로 유효한 모드에서 이 응답을 `deny`로 바꾸면 그 확인 창은 열리지 않는다. 다만 배포에 의존하는 다음 단계는 여전히 못 한다. 완료 기준에 **같은 세션에서 독립적인 다음 일 하나가 실제로 끝났는지**를 추가하자. 절전 방지는 전원 연결·뚜껑 열림·유효한 assertion이 유지되는 동안의 유휴 잠자기가 대상이다. 시작 때 점검했다고 이후 뚜껑을 닫아 잔 사건까지 해결했다고 볼 수는 없다.

**더 작은 해법:** 같은 계정의 여러 worktree가 끝 시각 하나를 공유하는 결정은 유지하자. 세션 등록이나 별도 감시 프로세스는 필요 없다. 대신 아침 목록의 중복 합치기는 `report`에서 해도 된다. guard는 짧은 제한 시간 안에 가린 항목 한 줄만 추가하고, `report`가 같은 키의 첫 시각·마지막 시각·횟수를 묶는다. 이것이면 매번 전체 파일을 다시 쓰지 않고도 아침에 보는 결과는 같다. 목록 파일 자체가 반드시 키당 한 줄이어야 한다면 기존 저장 방식을 유지하되 아래 잠금 시간 제한은 필요하다.

### 1. 아침 목록을 쓰려다 정작 거절 응답을 못 보낸다

모든 레포가 같은 `queue.lock`을 쓴다. 한 프로세스가 잠금을 쥔 채 지연되고 다른 guard가 차단형 `flock`에서 기다리면 예외가 발생하지 않는다. 훅의 15초가 먼저 끝나면 **이미 `deny`여야 한다고 정한 명령도 거절 응답 없이 실행될 수 있다**. 이는 기획서가 이미 실측한 시간 초과 동작의 귀결이다. 설계의 “away 처리 전체 오류 → ask”와 위험 절의 “목록 기록 실패 → deny”도 같은 입력에 다른 결과를 약속한다.

**확인 방법:** `hooks/hooks.json:27`의 제한과 `scripts/guard.py:177` 이하의 이유 계산·응답 순서를 대조한다. S3에는 격리 HOME에서 테스트 프로세스가 `queue.lock`을 잡은 채 놓지 않는 경우를 넣고, JSON을 stdin으로 guard에만 넣는다. 유효 상태에서는 잠금을 계속 잡고 있어도 15초보다 충분히 일찍 `deny`와 **기록 실패** 이유가 와야 한다. 같은 명령에 상태를 읽지 못하면 `ask`, 원래 확인 대상이 아니면 출력 없음이어야 한다. 이 세 갈래를 따로 검사해야 깨진 상태 파일 시험만 통과하는 구현을 걸러낸다.

### 2. 전역 `on` 두 번 뒤, `off`가 성공해도 Mac은 계속 깨어 있다

두 탭이 동시에 꺼진 상태를 읽고 각각 caffeinate를 띄운 뒤 상태를 저장하면 마지막 pid만 남는다. `off`가 그 pid를 종료하고 assertion 해제까지 확인해도 첫 pid의 assertion은 만료까지 남을 수 있다. 순차적인 `on → status → off`는 이 경우에도 통과한다. 반대로 재부팅 뒤 다른 프로세스가 같은 pid와 흔한 인자(`-i -s -t 10800`)로 떠 있다면 `ps` 인자 일치만으로는 종료할 소유권을 확인할 수 없다.

**확인 방법:** 기획서 ‘동작 1·3’의 교체 순서와 ‘설계’의 `queue.lock` 적용 대상을 읽는다. S2의 가짜 전원 명령으로 두 `on`의 시작을 겹치게 하고 마지막 `off` 뒤 **가짜 assertion 전체**가 비었는지 센다. 별도 fixture에서는 pid·인자는 같고 시작 시각만 다른 프로세스를 돌려주어 종료 신호가 가지 않았는지 확인한다. 상태 전환 전체를 직렬화하고 프로세스 시작 식별값까지 대조하자. 해제를 확인할 수 없으면 메뉴 앱에 `caffeinate_released:true`를 반환하지 않아야 한다.

### 3. 200자 가림을 통과한 값이 다른 프로젝트 대화에 들어간다

예컨대 `cdk deploy Demo --parameters License=DEMO_MARKER`에서 `License`는 열거된 가림 패턴에 없다. 이런 인자 값을 보관하면 같은 계정의 다른 프로젝트를 아침에 열었을 때 SessionStart가 그 명령까지 대화에 붙인다. 정상적인 키 중복·건수 시험은 모두 통과한다. 반대로 긴 공통 접두부 뒤에서만 대상이 다른 두 명령은 해시는 달라도 화면의 200자는 같아 사용자가 무엇을 검토할지 모른다.

**확인 방법:** S3에서 위 **가짜 표식**과 200자 뒤에서 대상이 갈리는 더미 입력 두 개를 사용한다. `queue.jsonl`, `report --json`, 다른 레포의 SessionStart 출력에 표식이 없는지, 두 대상은 구분되는지 각각 검사한다. 표시용 요약은 명령 종류·식별 가능한 안전한 대상·레포로 만들고 미분류 인자 값은 생략한 뒤 200자로 제한하자. 전체 명령 해시는 중복 판정에만 쓴다. 다른 레포의 시작 알림에는 건수와 `away.py report` 조회법이면 충분하다.

**그 밖에 고정할 계약**

- `--json`은 인자 오류(2)까지 포함해 stdout에 JSON 하나만 내고 안내는 stderr로 보낸다. S2는 키 존재뿐 아니라 꺼짐·자연 만료·켜졌으나 assertion 없음 각각의 `active/expired/alive`, 시각의 타입·null, 중복된 1건의 `queue_count` 의미를 검사해야 앱이 표시를 결정할 수 있다.
- 동작 3은 만료 시 삭제·요약 출력도 약속하지만 그 시각에 실행되는 것은 `caffeinate -t`뿐이다. `now >= until`에서 즉시 판정만 바뀌고, 파일 정리와 해제 확인은 다음 어떤 호출이 맡는지 명시하자.
- `~/.config`는 Mac 전체가 아니라 같은 HOME 기준이다(`scripts/kitlib.py`, `CONFIG_DIR`). 또한 macOS에서 전원 조회가 실패한 `unknown`과 실제 AC를 구분하고, 배터리 거부 시험과 별개로 “AC를 확인하지 못함”의 끝 코드·메시지를 정하자.
