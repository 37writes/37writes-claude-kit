**추천: B — 메뉴 막대 앱에 질문 보류와 세션 상태 표시까지 넣는다.** 회의에 들어가기 전 시각을 한 번 고르면, 이미 맡긴 일 중 답 없이 할 수 있는 일은 계속하고, 돌아왔을 때 어느 탭에 무슨 답을 주면 되는지 보여 주는 앱이다. 끝 시각은 자리 비움 정책의 만료 시각이다. 에이전트를 시작하거나 그 시각에 강제 종료하는 예약은 아니다.

**1. 무엇이 아직 멈추는가.** 실측은 도입 전 배포 확인 창 1건(6시간 58분), 잠자기 5회다. 도입 후 확인된 것은 더미 bypass 세션에서 Bash 거절 뒤 독립 작업 하나를 끝냈다는 것까지다. 후보별 실제 빈도는 **미확인**이다. 아래는 사용자 발언, 주로 쓰는 모드, 한 번 막혔을 때 잃는 작업량을 기준으로 한 조사 순서다.

| 순서 | 남은 원인 · 영향 | kit가 할 수 있는 일과 한계 |
|---|---|---|
| 1 | **(a) 질문.** 반복 질문은 사용자가 직접 호소했다. 질문 창과 글로 묻고 끝낸 턴의 비율은 모른다. | 공식 문서상 `PreToolUse`는 `AskUserQuestion`에 매칭되고 `deny`로 호출을 거절할 수 있다. 기존 matcher는 `Bash`뿐이다. 질문 거절이 Orca 대화형 탭에서 창 없이 다음 작업으로 이어지는지는 **미확인**. 글로 한 질문은 도구 호출이 없어 이 방법으로 잡히지 않는다. |
| 2 | **(b) 독립 작업이 남았는데 턴 종료.** 한 탭은 다음 입력까지 조용해지고 다른 탭은 계속할 수 있다. | 정상 응답 끝의 `Stop`은 기록하거나 `decision:block`과 이유로 계속시킬 수 있다. 하지만 남은 일이 **이 탭에 승인된 독립 작업인지**는 종료 이벤트로 알 수 없다. 이미 끝난 턴을 나중에 모드만 켜서 깨우지도 못한다. |
| 3 | **(e) 배포가 진짜 선행 조건.** 원래 사건에서 확인된 것은 창 대기였지 이후의 모든 일이 배포에 의존했다는 사실은 아니다. | guard는 명령을 거절·기록한다. 대체 작업이 없다면 **‘배포 승인 필요’로 종료가 정답**이다. 훅으로 의존성을 없앨 수 없다. |
| 4 | **(d) 사용 한도·API 오류·로그인 만료.** 여러 탭에 동시에 영향 가능. | 문서상 오류로 끝난 턴은 `Stop` 대신 `StopFailure`가 종류를 알려 주며 종료를 번복하지 못한다. 기록은 가능하지만 훅이 한도나 자격을 복구할 수 없다. 한도 리셋 대기 등 모든 경우가 오류 종료 이벤트를 낸다는 보장은 없다. |
| 5 | **(f) Orca 워커 대기·gate.** 부모 답장·선행 워커·사람 승인이 필요하면 연결된 작업만 대기한다. | 정상적인 인계·대기일 수 있다. Claude의 `Stop`은 Orca의 gate 상태를 모르며 승인 주체도 아니다. 원인 표시는 Orca의 명시적 대기 신호가 있을 때만 한다. |
| 6 | **(c) 비-bypass 탭의 자체 권한 창.** 주 사용 방식에서는 노출이 낮지만 해당 탭은 밤새 기다릴 수 있다. | kit Bash 판정 밖이다. 문서상 `PermissionRequest`에서 일반 도구 요청을 거절할 수 있지만 샌드박스 네트워크 창 등은 제외된다. 이번에는 신호가 있으면 표시만 하고 권한 모드를 바꾸지 않는다. |

전원은 위 여섯 가지와 별개다. 시작 뒤 전원을 빼거나 뚜껑을 닫거나 절전 방지 프로세스가 죽으면 여러 탭이 함께 영향을 받는다. 빈도 판단은 첫 실사용부터 **세션별 명시적 대기 횟수와 해소까지의 시간**으로 갱신한다. 긴 무활동 시간을 손실 시간으로 세지 않는다.

**2. 아침에 무엇이 남는가.**

| 선택 | 돌아왔을 때 볼 결과 · 비용 |
|---|---|
| A 앱만 | 거절된 명령은 보이지만 답을 기다린 탭은 여전히 질문 창에 있을 수 있다. 구현 비용은 가장 낮다. |
| **B 앱 + 질문 보류** | 거절한 명령과 짧은 질문 요지·해당 탭이 남는다. 거절 이유로 이미 승인된 독립 작업을 안내한다. 첫 선택지를 사용자 답으로 보내지 않는다. 되돌릴 수 있는 구현 선택만 가정으로 기록하고, 범위·비용·승인이 달라지면 보류한다. 글로 묻고 종료하는 경우는 남는다. |
| C B + 종료 차단 | 조기 종료 한 번을 건질 수 있지만 완료·gate·배포 대기까지 깨우면 같은 시도와 과금만 쌓인다. `stop_hook_active`와 자체 상한 없이 야간 전체에 적용하지 않는다. 실측 후 명시적 미완료 체크포인트가 있는 세션에만 검토한다. |
| D 허용 목록 통과 | 실제 배포 뒤 다음 작업까지 끝날 수 있는 대신 잘못된 배포도 이미 일어난 뒤다. 같은 계정의 상태 파일만으로 사람의 사전 승인을 증명할 수 없다. 사용자가 미룬 별도 권한 설계다. |

**3. 패널에는 ‘모드’와 ‘작업’을 따로 표시한다.** `내일 08:00까지 · 지금 끄기` 아래에 `전원 연결 · 절전 방지 중`과 `관측된 탭 2개: A 마지막 도구 01:12 / B 턴 종료 01:16`을 둔다. 시작 전에는 최대 12시간과 **같은 계정의 kit 적용 Claude 탭 전체**라는 범위를 보인다. 시작 후 전원 분리·절전 방지 해제는 경고로 바꾼다. 로그인 시 실행은 설정으로 옮기고, 앱만 열며 모드를 켜지는 않는다.

현재 `status`에는 세션 활동이 없고 `report`도 레포·명령으로 묶어 탭 구분이 사라진다. 최소 추가 기록은 활성 기간의 세션 ID·worktree·최근 이벤트 종류·시각이다(도구 사용, 정상 종료, 명시적 대기/오류). 질문 내용은 별도 목록에 짧게 가려서 남긴다. 모르는 탭은 `관측 안 됨`, 장시간 조용한 탭은 `마지막 관측 HH:MM`으로 둔다. 멈춤 알림은 확인된 대기·오류에만 한 번, 야간 기본은 배지다. 아침 목록에는 이전 회차를 구분하고 자동 재실행 버튼은 두지 않는다.

**4. 앱은 `away.py`의 JSON 계약을 호출한다.** 상태 파일 단독 조회로는 현재 전원이나 기록된 PID가 같은 `caffeinate`인지 알 수 없다. 직접 제어하면 잠금·만료·목록 병합까지 Swift와 Python이 따로 판단한다. 앱은 `on/off/status/report --json`만 호출하고 세션 정보는 호환 가능한 조회 필드로 확장한다. GUI에 `CLAUDE_PLUGIN_ROOT`가 있다고 가정하지 않는다. `claude plugin list --json`에서 활성 kit의 `installPath`를 찾고 갱신 후 경로가 사라지면 재탐색한다. 후보가 여럿이거나 개발용 설치면 최초 한 번 위치를 선택한다. GUI에서 찾은 Python 3와 절대 경로를 셸 문자열 없이 실행하고, 없으면 설치 안내를 띄운다. `py.sh`는 Python이 없어도 코드 0이라 **유효한 JSON과 `ok`까지** 확인해야 켜짐으로 표시할 수 있다.

출시 전 확인할 반례 세 가지: ① 대화형 bypass 탭에서 질문 거절 뒤 창 없이 다른 승인 작업이 끝나고 아침에 질문이 한 건 남는가. ② 긴 테스트 중인 탭과 배포 승인만 남은 탭이 동시에 있을 때 전자를 정지라고 오보하거나 후자를 다시 깨우지 않는가. ③ 플러그인 갱신 또는 Python 부재 뒤 올바른 설치를 다시 찾거나 시작 실패를 표시하는가.
