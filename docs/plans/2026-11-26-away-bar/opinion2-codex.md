global.openai.gpt-6.2-astra (Codex)

**제안: 떠나기 전에 ‘어느 탭이, 무엇까지 끝내면 되는지’를 고른다.** 예컨대 “스테이징에 이 변경을 한 번 배포하고 가입 시험까지”다. 종료 시각은 새 작업·배포를 시작할 권한의 만료이지, 그때까지 토큰을 쓰라는 뜻이 아니다. 원래의 6시간 58분 대기를 해결하는 기준은 질문 수가 아니라 **배포에 의존한 가입 시험 결과가 아침에 있는가**다. 이번 요청은 사전 승인 설계를 논의할 근거이지 특정 배포의 승인은 아니다.

**1. 글로 묻고 끝내는 탭 — 남은 단계가 있을 때만 한 번 이어간다.** 현재 `hooks.json`은 세션 시작·요청 때 안내하고 Bash 직전만 검사한다. 글로 한 질문에는 도구 호출이 없고, `away.py` 알림은 이미 끝난 턴을 깨우지 못한다.

| 선택 | 아침에 볼 최악의 결과 |
|---|---|
| 훅 제거, harness 문구만 유지 | “어느 이름으로 할까요?”가 마지막 줄이고 시험은 손도 대지 않았다. |
| 초안처럼 모든 정상 종료를 한 번 차단 | 여러 탭이 완료 보고를 다시 쓰거나 정산된 워커가 다음 일을 찾는다. |
| **추천: 선택한 일반 탭 + 아직 실행 가능한 승인 단계가 있을 때만 계속** | 남은 단계 기록이 낡으면 한 번 헛돌거나 일찍 끝난다. |

출발 시 해당 탭에 다음 단계와 완료 증거를 붙인다. `AskUserQuestion`은 활성 탭에서만 deny하고 가린 질문 요지를 남긴다. 글로 물었어도 미완료 독립 단계가 있으면 `Stop`이 그 단계명을 돌려준다. 되돌릴 수 있는 선택만 기본값으로 기록한다. **반례:** 승인이 필요한 배포만 남으면 재촉해도 할 수 있는 일이 없다. 이때는 `배포 승인 대기`로 끝낸다. 같은 단계당 1회, 회차·세션당 최대 2회로 재개 횟수를 원자적으로 제한하고 `stop_hook_active=true`·만료·완료면 통과한다. 마지막 이벤트는 `턴 종료`일 뿐, 결과 증거나 명시적 대기 사유 없이 `완료/멈춤`으로 표시하지 않는다.

[Claude Code 훅 문서](https://code.claude.com/docs/en/hooks#stop)는 정상 응답의 `Stop`에서 `decision:block`과 `reason`으로 재개하고 서브에이전트 종료에는 `SubagentStop`을 쓴다고 명시한다. `claude --help`(2.1.332)는 bypass 옵션을 확인해 줄 뿐, Orca 대화형 bypass에서 질문 거절→재개 순서는 **미확인**이다. 서브에이전트에는 차단 훅을 등록하지 않는다. Orca 워커는 `ask`·gate·`worker_done` 뒤 종료가 계약이므로 애초 재개 대상에서 제외한다(역할 불명이면 제외). 정산과 Stop 도착 순서도 **미확인**이다. 출시 시험은 일반 탭의 글 질문 뒤 더미 시험 1건 완료, 워커 정산 뒤 추가 턴 0건, 서브에이전트 반환 뒤 재개 0건으로 나눈다.

**2. 배포 없이는 다음 단계가 불가능 — ‘배포 명령’ 대신 검토한 변경 한 건을 승인한다.** 지금 `decide()`는 확인 사유가 있으면 자리 비움 동안 거절한다. 다른 일을 고르는 것만으로는 배포 후 시험을 마칠 수 없다.

| 선택 | 아침에 볼 최악의 결과 |
|---|---|
| guard 전체 끄기 | 다른 bypass 탭의 강제 push나 운영 삭제까지 확인 없이 끝난다. 앱에 이 스위치는 두지 않는다. |
| 레포+규칙 또는 정확한 명령을 시각까지 허용 | 같은 명령이 바뀐 산출물·다른 계정에 적용되거나 두 탭에서 중복 실행된다. 지금 CDK 규칙 한 줄은 deploy와 destroy도 함께 묶는다. |
| **추천: 스테이징에서 사용자가 검토한 변경 세트 1개만 실행** | 범위 안의 코드 결함으로도 서비스가 깨질 수 있다. 실패를 기록하고 의존 작업을 멈춘다. |

요청 파일·최근 거절 목록은 **후보**일 뿐이다. 출발 전 실제 `cdk diff`와 준비된 변경 세트를 보여 주고, 레포·worktree·세션·검증한 SHA와 산출물 digest·계정/리전/스택·변경 세트 ID·만료를 고정한다. **반례:** 승인 뒤 다른 탭이 같은 스택을 바꾼다. 실행기가 직전에 대상과 기존 상태를 재확인하고 잠금 안에서 1회를 소비한 뒤 같은 변경 세트만 실행한다. 불일치·만료·기록 실패면 시작하지 않는다. 포괄적 `allow` 대신 전용 실행기가 자격·대상을 제한한다. 강제 push·삭제/교체·IAM·시크릿·마이그레이션·파괴 명령은 후보에서 제외한다. 실패·결과 불명은 재시도나 자동 롤백 없이 중단한다. 아침에는 승인·시도·실제 결과를 구분하고 실행 ID와 후속 시험 결과를 남긴다.

`deploy_gate.py`는 고정 SHA push의 원격·fast-forward·양쪽 정책·검증 기록·제외 경로를 검사한다. 이 경로는 그대로 쓰고 실패를 야간 승인으로 덮지 않는다. SHA 검증·기록 형식은 공유하되 직접 CDK는 별도 실행기와 스택 결과 확인이 필요하다. harness의 인프라 T2 명시 승인은 위 변경 세트 검토로 충족시키며, 떠난 뒤 새로 생긴 변경까지 승인한 것으로 보지 않는다. 같은 UID의 파일·훅은 사람 서명을 증명하지 못한다. 실제 강제가 필요하면 별도 CI 역할이 승인된 변경 세트만 실행하고 로컬 에이전트에 동등한 AWS 쓰기 자격이 없어야 한다.

**3. 글 속 `cdk deploy` — 데이터임이 확인된 부분만 검사에서 뺀다.** `RULES`는 Bash 입력 전체에 `re.search`한다. `command_words`는 일부 규칙에만 쓰이고, 앞단의 `re.split`은 인용·heredoc 경계를 모르며 `shlex.split`은 인용 정보를 잃는다.

| 선택 | 아침에 볼 최악의 결과 |
|---|---|
| CDK 훅 제거 | 글은 쓰였지만 실제 무승인 배포도 놓쳤다. |
| 초안처럼 표시 명령의 인자·heredoc 일괄 제외 | 겉으로는 글인 인자 안의 셸 실행까지 빠진다. |
| **추천: 인용·리다이렉션·중첩 실행을 보존해 해석한 뒤 리터럴만 제외** | 판별 불가한 스크립트는 여전히 보류될 수 있다. 이유를 별도로 표시한다. |

**반례와 인수 시험:** ① `printf '%s' "$(cdk deploy Demo)"`의 인자는 출력 전에 실행된다. ② `sh <<'EOF'`의 다음 줄이 `cdk deploy Demo`이면 인용된 본문도 셸의 코드다. ③ `sh -c 'cdk deploy Demo'`는 인용된 인자가 실행 대상이다. 세 문자열을 **실행하지 않고** `test_guard.sh` 방식의 stdin JSON으로 주어 평소 `ask`, 자리 비움 `deny`를 요구한다. 대조군 `git commit -m 'cdk deploy Demo'`와 `cat <<'EOF'`의 같은 본문은 양쪽 모두 `none`이어야 한다. SQL 도구의 쿼리 등 실행 인자는 유지하고 `eval`·`xargs`·스크립트 파일은 안전한 리터럴로 취급하지 않는다. 해석할 수 없는 위험 후보는 기존 확인으로 돌린다.

**순서:** ① 오탐 회귀시험과 guard 수정은 앱과 별도로 먼저 낸다. ② 앱과 선택 탭 재개를 붙여 무권한 더미 작업으로 검증한다. ③ 같은 제품 목표 안에서 단일 스테이징 배포 승인을 별도 단계로 낸다. 두 탭의 중복 요청과 승인 뒤 변경이 차단되고, 정상 건은 배포 후 시험까지 끝나야 ‘배포 의존 작업 지원’으로 표시한다. 이번 검토는 문서·소스·CLI 도움말 대조이며 새 훅과 배포는 실행하지 않았다.
