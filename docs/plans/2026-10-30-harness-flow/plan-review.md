## 반례 1 — 검증한 SHA·원격과 실제 push가 어긋난다

**중요도: 높음. 자동 배포를 열기 전에 보완.**

기획의 guard 1~5는 명령 문자열, 로컬 ref와 검증 기록을 대조하지만 실제 push가 같은 커밋을 같은 저장소에 보낸다는 조건이 빠져 있다.

- `verify S` 뒤 `git push origin main`을 검사할 때 `main == S`이면 통과한다. 검사와 실제 Git 실행 사이에 다른 탭이 같은 브랜치를 T로 전진시키면 Git은 T를 보낼 수 있다. T의 검증 기록은 없어도 이미 끝난 PreToolUse 검사는 다시 실행되지 않는다. worktree를 분리해도 같은 레포의 ref는 공유한다.
- `origin`이라는 이름이 같아도 fetch URL과 push URL은 다를 수 있다. `remote.origin.pushurl`이 다른 저장소를 가리키면 `refs/remotes/origin/main`은 실제 배포 대상의 기준 커밋이라는 증거가 아니다. 실제 대상이 S의 조상을 가리키면 강제 옵션 없이도 push가 성공할 수 있다.

**코드·기획 근거**

- `scripts/guard.py:109`~`123`: Git 전역 인자를 먼저 처리하고 push 인자만 남긴다. 특히 `:115`에서 `-c`와 그 값을 버린다. 새 `push_allowed(repo, args)`를 이 지점에 붙이면 일회성 원격 설정 변경 정보가 전달되지 않는다.
- `hooks/hooks.json:20`~`27`: guard는 Bash 실행 **전** 훅이다. 실제 실행 시 ref를 고정하는 구조가 아니다.
- `scripts/kitlib.py:26`~`29`: 별도 Git 프로세스로 조회한다. 검사 대상 Bash 명령의 `git -c ...`를 자동으로 공유하지 않는다.
- 기획 `:64`, `:66`, `:69`~`74`: SHA 기록 자체는 좋지만 `main`처럼 움직이는 src와 원격 이름을 허용한다. `:103`의 “원격 추적 ref가 오래되면 더 엄격”도 원격이 되감긴 경우에는 성립하지 않는다. 로컬 base보다 실제 원격이 뒤로 갔으면 실제 재반영 범위가 `base..SHA`보다 커진다.

**왜 현재 완료 기준으로 놓치는가**

완료 기준 f는 고정된 로컬 fixture에서 정책·SHA·범위·기록을 검사한다. 검사 후 ref 이동이나 fetch/push 대상 분리는 요구하지 않는다. 판정 함수의 모든 테스트가 통과해도 실제 송신은 달라질 수 있다.

**확인 방법**

구현 후 테스트 전용 레포와 로컬 bare 원격 A/B에서 확인한다. 실제 서비스 원격은 사용하지 않는다.

1. S를 검증하고 `git push origin main`의 훅 판정을 받는다. 판정 후 실행 전 멈추는 테스트 장벽에서 `main`을 미검증 T로 옮긴다. 실행 결과 원격 T가 되면 실패다. 안전한 결과는 S만 반영되거나 ask/거부다.
2. fetch URL=A, push URL=B로 설정하고 두 원격의 기준 커밋·정책을 다르게 둔다. B에 대한 근거 없이 A의 추적 ref로 자동 허용하면 실패다. `git -c remote.origin.pushurl=... push origin main`도 같은 조건으로 확인한다.

**더 작은 보완**

자동 경로는 검증된 **전체 SHA를 src로 쓴 단일 refspec**으로 제한한다. Git 전역 설정 재정의는 자동 경로에서 거부하고, 실제 push URL·단일 목적지·기준 ref 확인을 명세한다. 최신 기준을 확정하지 못하면 ask로 돌아간다. guard 4의 기록 대조와 5의 diff 검사는 이 확정된 SHA·기준에 대해 수행해야 한다.

guard 6의 기록 보호는 현재 Bash 전용 훅 구조상 권한 경계가 아니다. 기획이 이미 best-effort라고 인정했으므로 별도 반례로 세지는 않는다. “일부 직접 쓰기를 ask로 만든다”는 검사 결과를 “위조 불가능”으로 표현하지 않는 것이 조건이다.

## 반례 2 — 오래된 worktree 복사본이 완료한 작업을 다시 재개시킨다

**중요도: 높음. 재개 목록의 선택 규칙 보완.**

작업 A의 기획서를 포함한 시점에서 무관한 worktree B를 만든다. 이후 A가 작업을 끝내 기획서를 `done`으로 바꾸고 main에 병합한 뒤 A를 정리한다. B에는 같은 상대 경로의 `in-progress` 복사본이 남아 있다.

기획대로 활성 상태만 모으고 비기본 worktree를 우선하면 main의 `done`은 빠지고 B가 후보로 남는다. B에서 별도 커밋을 했다면 B의 브랜치 자체는 main에 병합되지 않았으므로 “상태 확인 필요” 조건도 걸리지 않는다. “하나면 바로” 흐름이 B로 이동해, B의 오래된 실제 파일·로그와 일치하는 미완료 단계를 다시 수행할 수 있다. 선택한 worktree 안에서만 대조해서는 이미 다른 곳에서 완료했다는 사실을 찾지 못한다.

**코드·기획 근거**

- `skills/plan/SKILL.md:50`, `:56`, `:87`~`90`: 기획의 식별자는 날짜·slug 상대 경로이며 상태와 체크박스가 파일 안에 있다. worktree 복사본을 구별하는 소유권 정보는 없다.
- `skills/harness/SKILL.md:130`~`131`: 병합과 기획서 완료 갱신은 수행하지만 다른 worktree에 남은 복사본은 갱신하지 않는다.
- `scripts/session_start.py:23`~`33`: 현재 재개 정보는 레포 하나의 마지막 기록에서만 읽는다. 여러 worktree의 상태 충돌을 해결하던 기존 동작을 재사용할 수 없다.
- 기획 `:44`: 동일 상대 경로는 비기본 worktree 우선, `done`·`abandoned` 제외, 브랜치 병합 여부로 경고한다. 기획 `:46`: 후보 하나면 바로 재개한다. **작업 완료 여부와 그 복사본이 있는 브랜치 전체의 병합 여부는 다르다.**

**왜 현재 완료 기준으로 놓치는가**

완료 기준 c는 다른 worktree의 진행 중 기획서 표시와 종료 상태 제외만 확인한다. 서로 다른 상태를 가진 동일 경로 복사본의 조합은 없다. “done이 목록에 안 나온다”를 만족시키는 구현이 오히려 완료 사실을 버릴 수 있다.

**확인 방법**

구현 후 위 A/B/main 순서를 fixture로 만든다. main은 `done`, B는 같은 기획서가 `in-progress`이고 B에 무관한 커밋이 있어야 한다. main에서 SessionStart와 “이어서 해줘”를 실행해 B를 자동 재개하지 않는지 확인한다. 여러 활성 복사본이 서로 다른 체크박스를 가진 경우도 한쪽을 조용히 버리면 실패다.

**더 작은 보완**

종료 상태를 버리기 **전에** 같은 경로의 모든 복사본을 비교한다. 상태·진행도가 충돌하면 경로 우선순위로 고르지 말고 충돌 후보로 표시해 자동 재개를 막는다. 최소 버전에서는 불확실한 후보를 사용자에게 고르게 해도 된다. 브랜치 전체의 병합 여부는 보조 정보로만 쓴다.

## 반례 3 — 프로필 없이 시작한 작업이 다음 세션의 자동 재개에서 빠진다

**중요도: 중간. 지원 경로와 초기화 정책의 연결 보완.**

README·AGENTS.md에 작업 정보가 충분한 기존 레포에서 사용자가 “기능 만들어줘, 프로필은 추가하지 마”라고 한다. 기획대로 기존 파일을 보존하고 `docs/plans`만 만들어 작업하다 세션을 끝낸다. 다음 세션을 Orca 밖에서 열면 이 레포는 kit 프로젝트가 아니므로 SessionStart는 재개 목록도 harness 안내도 출력하지 않는다. 패널 역시 kit 프로젝트로 인식하지 않는다.

harness가 자연어를 보고 다시 호출될 가능성은 있지만, **hook 목록이 없는 경우에도 어디서 재개 목록을 직접 얻는지**가 정의되지 않았다. 따라서 사용자가 명령이나 파일 경로를 다시 설명하지 않아도 같은 작업을 이어받는다는 보장이 없다. 이는 kit 판정을 `docs/plans`로 넓히자는 주장이 아니다. 초기화하지 않을 권리와 자연어 재개를 함께 지원하려면 두 기능을 분리해야 한다.

**코드·기획 근거**

- `scripts/kitlib.py:32`~`37`, `scripts/session_start.py:10`~`13`: kit 판정 실패 시 시작 안내 자체가 종료된다. 기획 `:43`, `:45`는 판정 기준을 바꾸되 이 종료 구조는 유지한다.
- `scripts/orca_context.py:16`~`17`, `:26`~`28`: 모든 레포에 안내를 주는 다른 경로도 Orca 환경에만 적용된다.
- `hooks/panel.tsx:41`~`47`: 현재도 kit 여부가 프로젝트 상태 읽기의 조기 반환 조건이다. 새 패널에서 비-kit의 사용자가 요청한 재개 조회를 어떻게 지원할지는 기획에 없다.
- 기획 `:53`, `:83`: 프로필 없이 작업 기획만 만드는 경로를 명시적으로 허용한다. 기획 `:46`은 “재개 목록에서 고른다”라고만 정한다.

**왜 현재 완료 기준으로 놓치는가**

완료 기준 b/c를 각각 다른 새 세션에서 통과시킬 수 있다. “프로필 없는 작업 생성 → 중단 → Orca 밖 새 세션에서 자연어 재개”의 연결 검사는 없다.

**확인 방법**

프로필·devlog가 없는 fixture에서 자연어 요청으로 기획서를 만들고 미완료 상태로 중단한다. Orca 환경 변수가 없는 새 Claude 세션에 플러그인을 로드하고 “이어서 해줘”만 입력한다. 기존 기획서와 실제 변경을 찾아 이어가며 프로필 생성이나 `/kit:init` 입력을 요구하지 않아야 한다. hook 직접 실행과 실제 모델의 파일 읽기를 함께 확인한다.

**더 작은 보완**

`kit_repo`는 자동 훅 설치·자동 안내를 위한 opt-in 판정으로 유지한다. harness의 명시적 “이어서” 의도는 kit 판정과 독립적으로 현재 git 루트의 `active_plans`를 호출하도록 정한다. 무관한 레포에는 아무것도 자동 설치하지 않으면서, 사용자가 요청한 읽기 전용 재개 탐색은 가능하다.

## 검토 증거와 한계

기준 HEAD가 `4ebd72e`이고 시작 시 작업 트리가 깨끗함을 확인했다. 기획과 위에 인용한 스킬·Python·훅·패널 코드를 읽었고, `git worktree list --porcelain`에서 현재 레포의 실제 worktree와 대상 기획 상태도 읽기 전용으로 확인했다. `deploy_gate.py`와 `active_plans`는 아직 구현 전이다. 위 fixture 절차는 **추가해야 할 확인 방법**이며 실행해 통과했다고 주장하지 않는다. 읽기 전용 제약에 따라 fixture 레포·worktree를 새로 만들거나 다른 에이전트를 실행하지 않았다. 이번 산출물은 이 보고서 하나다.
