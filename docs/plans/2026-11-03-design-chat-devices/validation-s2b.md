## 3. 독립 실패·경계 시나리오 2개

### 경계 1: 질문의 일부를 선택한 상태에서 출처를 확인하고 돌아온다

- 선택 이유: 서로 합리적으로 보이는 두 계약을 같은 조작에 적용했을 때 합격 기준이 양립하는지 확인한다. 단순히 계약 행마다 별도 fixture를 만들면 숨겨지는 충돌이다.
- 정적 재현: `git show 0da62ab:skills/design/references/conversational.md`의 :17·:19를 읽고, 상태를 `초점=입력, 선택=질문의 일부` → 사용자가 출처 칩으로 이동해 열기 → 닫기로 따라간다.
- 실제 모의 결과: :17 확인 방법대로면 마지막 초점은 처음 입력과 같아야 한다. :19대로면 마지막 초점은 칩이어야 한다. 입력 내용·선택을 보존하면서 칩에 복귀하는 구현이 한쪽 검사에서 잘못 실패한다. A 수정 필요.
- 미검증: 브라우저별 터치 초점·선택 API 동작과 실제 입력 복귀는 수행하지 않았다. 특정 제품의 버그를 관찰한 것이 아니라 문서의 합격 조건 충돌을 재현했다.

### 경계 2: 접힘 없는 편집 부품과 비모달 메뉴를 재사용하는 새 채팅

- 선택 이유: 기존 프로필을 유지한다는 규칙이 특정 채팅 구현을 복사하라는 규칙으로 변하지 않는지 확인한다. 사용자는 외장 키보드로 입력하며, 기존 편집기는 별도 접힘 미리보기 없이 유연한 높이를 쓰고 메뉴는 비모달 disclosure라고 가정한다.
- 정적 재현: `git show 0da62ab:skills/design/SKILL.md`의 :16·:38, `system.md`의 :3·:66·:69, `conversational.md`의 :9·:32–44·:49·:52·:74·:120을 함께 적용한다. 접힌 입력·clip-path·Tab 격리를 채택하지 않아도 7개 사용자 동작 계약을 충족할 수 있는지 읽는다.
- 실제 모의 결과: 기존 방향 유지와 배치 선택 선언은 이 구성을 허용한다. 그러나 실패 유형의 명령형 “규칙”과 추가 행을 그대로 적용하면 접기/줄 스냅/특정 이벤트를 도입하고 좁은 메뉴를 격리해야 한다. 입력은 키보드 focus로 들어갈 수 있어야 하는데 “탭할 때만 펼침”까지 재사용 부품의 입력 경로와 충돌한다. B·C·D의 조건부 적용·웹 예시 구분이 필요하다.
- 미검증: 특정 웹 프레임워크·네이티브 플랫폼의 실제 편집/메뉴 구현과 접근성 API는 실행하지 않았다. 다른 스택에서 동등한 사용자 결과를 내는 코드의 정확성까지 판정하지 않는다.

추가로 요청된 작은 수정 경계도 정적으로 적용했다. 채팅 메뉴 버튼 라벨 하나 수정에서는 기존 방향·관련 메뉴 부품을 유지하고 영향 폭·전환점·확대·키보드/터치 행을 고를 수 있다. 하지만 C:126 때문에 그 메뉴 행마다 초안·캐럿·출처·중지 조작까지 추가되는 문제가 남는다(F). 문서를 읽는 행위 자체보다 전체 시퀀스를 의무화한 문장이 수정 대상이다.

## 5. 공개 필터

### 범위·방법

- 기준 원격 참조: `origin/main = fdc2663963b43efb6942a615e11d4ce50a8003c5`, 검사 HEAD는 위 대상 SHA. 원격 갱신·push는 하지 않았다.
- `git log -p --format=fuller origin/main..HEAD` 전체를 검사했다. 기본 명령의 내용에 작성자·커미터 메타데이터를 더한 범위다. **6개 커밋, 1,223줄, UTF-8 132,264바이트**, SHA-256 `860b54c5b7e4ae15f6cee796cb98a573ed680432866fd0a482ec4a6a2199c0ea`.
- 추가·삭제·문맥 줄, 메시지, 작성자·커미터·공동 작성자, 이전 기획·검토 보고서를 포함했다. 원문은 별도 파일로 저장하지 않았다. 주소·신원 후보는 출력에서 가리고 위치·분류만 기록했다.
- URL·이메일/도메인, 독립된 긴 계정형 숫자, 이미지 임베드·바이너리, 비밀값 형태를 패턴 검사하고, 전체 문장을 나누어 읽어 회사/고객/서비스명·내부 문서 제목·사내 질문·실제 수치를 문맥 분류했다. 기존 보고서의 “무노출” 주장을 필터 결과로 재사용하지 않았다.
- 아래 `log:N`은 위 fuller 명령의 출력 줄이다. 매칭 원문은 옮기지 않는다.

| 검사 항목 | 위치·분류와 결과 |
|---|---|
| 회사·고객·서비스명 | 메시지, README 및 플러그인 문맥, 설계 문서·기획/보고서에 공개 도구·플랫폼·프로젝트/역할명이 있다. 예: `log:8–18,45–62,104–105,255–259,663–672,1036–1043`. 특정 고객사·비공개 회사/서비스 식별명은 미발견. |
| 메타데이터·이메일 | `log:2,4,18,250,252,259,375,377,388,658,660,672,895,897,906,1116,1118,1125`의 18줄에 이메일 존재. 공개 이메일 제공자·공개 도구 제공자 도메인으로 분류했으며 작성자/커미터 이메일은 현재 저장소 설정과 일치. 이메일 “0건”으로 보고하지 않음. |
| 내부 URL·도메인 | HTTP(S) URL 후보 0건. 이메일 도메인은 위 분류. 전체 문맥에서 별도 내부 호스트·도메인·로컬 민감 서비스 경로 미발견. |
| 계정 ID형 숫자 | 10~16자리 독립 숫자 후보 0건. 기획/보고서에 Git SHA와 작업 식별자는 있으나 고객 계정 숫자로 분류할 내용 미발견. |
| 내부 문서 제목·사내 질문 원문 | 예시와 이전 삭제 줄까지 확인. 저장소 자체 기획/보고서 제목, 일반화된 UI 요구·경계 시나리오만 발견. 특정 내부 문서 제목·사내 질문 원문으로 식별할 내용 미발견. |
| 실제 데이터로 보이는 수치 | `conversational.md:10,69,75–80`에 비공개 프로젝트의 익명 UI 검증 집계·배치 수치·응답 표시 실측이라고 명시된 값이 있음. **합성 수치라고 분류하지 않음.** 업무/고객 데이터가 아니라 일반화한 UI 시험·배치 근거이며 이번 설계 4가 허용한 권장값 범위로 판단. 원본 측정의 진위·공개 승인 자체는 확인하지 않았음. |
| 기타 숫자 | 기획/보고서에 버전·날짜·폭·글자 확대·검사 집계·바이트/해시 등이 있음. 실제 고객 데이터로 보이는 수치는 미발견. |
| 이미지 | 이미지 임베드·data URI·바이너리 패치 후보 0건. 변경 파일 종류는 Markdown·JSON뿐. 캡처를 지시/언급하는 문장은 실제 이미지가 아님. |
| 비밀값 보조 검사 | 접근 키·개인키·긴 secret/API key/password 할당 형태 후보 0건. 보호 규칙과 검사 패턴 언급은 실제 비밀값으로 분류하지 않음. |

현재 범위에서 공개를 막을 구체적인 내부 정보 노출은 발견하지 못했다. 익명 프로젝트의 실측 수치가 있다는 사실과 고객 업무 데이터 유출은 구분했다. 비공개 조직의 전체 고유명 목록·원본 자료를 대조한 검증은 아니므로 모든 형태의 재식별 가능성을 증명하지 않는다. 이 보고서의 새 모의 사례도 합성 문서·일반 과업만 사용했으며 민감 매칭 원문을 포함하지 않는다.
