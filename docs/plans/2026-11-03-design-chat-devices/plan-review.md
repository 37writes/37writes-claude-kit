## 중요한 반례 3개와 확인 방법

### 반례 1 — 기존 블로그 메뉴 라벨 한 곳을 고치는데 모든 상황 표를 요구한다

기존 프로필과 테마가 있는 읽기 화면에서 메뉴 라벨만 길어졌다. 에이전트는 새 기기×상황 표와 기존 폭×모드 검사를 모두 채우려 하고, 존재하지 않는 채팅·시트·키보드 상태까지 만들거나 미완료로 남긴다. 표 작성 완료는 달성해도 작은 수정을 예측 가능한 비용으로 처리하지 못한다. 기존 `SKILL.md:36`의 작은 수정 범위와도 긴장한다.

- **수정 제안**: 주요 기기 상황을 먼저 고려한 뒤 변경 영향이 있는 행을 선택한다. 각 행에 `적용 / 비해당(이유) / 미검증(이유)`를 구분하고 대표 묶음의 근거를 적는다. 기존 프로필의 관련 조작·폭·전환점 검사는 유지하되, 미검증을 비해당으로 지우지 않는다.
- **확인 방법**: 새 세션에 기존 디자인 프로필과 “긴 메뉴 라벨 하나 수정” 요청만 준다. 레퍼런스 재선택 없이 영향받는 메뉴 폭·전환점·키보드/터치 접근을 고르는지, 채팅·시트는 생성하지 않고 비해당으로 설명하는지 검토한다. 새 규칙을 읽기 전후의 요청 질문 수·생성 문서·검증 행 차이도 비교한다.

### 반례 2 — 새 분석 화면의 방향 시안이 색만 다르고 중요한 배치 선택은 없다

프로필 없는 새 작업 화면에서 사용자는 “탐색 중심의 조밀한 화면”과 “결과 중심의 넓은 화면”을 비교하고 싶다. 10곳 조사와 3~4개 시안 요구를 모두 지켜도 배치를 고정한 탓에 색·서체만 다른 시안이 나온다. 완료 기준은 통과하지만 사용자가 여러 디자인 느낌을 보고 방향을 고르려던 목적은 해결되지 않는다.

- **수정 제안**: 같은 콘텐츠·핵심 과업·접근성·부품 의미를 비교의 공통 조건으로 두고 배치·밀도는 선택 축으로 허용한다. 조사 보드에는 출처 수 외에 패턴 차이, 사용자 과업에 유리한 점, 버릴 이유를 남긴다. 한 번 선택한 결과는 기존 프로필에 고정한다.
- **확인 방법**: 동일한 공개 가상 데이터·과업으로 두 방향의 설명 또는 시안을 만들게 한다. 색과 글꼴을 제거해도 탐색 위치·읽는 순서·정보 밀도의 선택 차이를 설명할 수 있어야 한다. 이후 “상세 화면 추가”를 주었을 때 새 레퍼런스 조사나 방향 선택을 자동 반복하지 않는지도 확인한다.

### 반례 3 — 모바일에서 긴 질문을 편집하며 이전 답을 스크롤하자 입력이 접힌다

좁고 짧은 화면에서 사용자가 여러 줄의 질문을 작성하다 이전 답이나 인용을 확인한다. “스크롤하면 접히고 키보드가 내려간다”를 그대로 적용하면 본문 스크롤·입력 내부 스크롤·자동 스크롤을 구분하지 못하고 편집 흐름을 끊을 수 있다. 얇은 바와 높이 상한을 맞춘 캡처는 통과해도 입력 지속성·초점·동작 도달성을 보장하지 못한다.

- **수정 제안**: 입력 내용과 선택 상태 보존, 명시적 사용자 조작에 따른 접기, 편집 중 자동 접기 방지부터 계약으로 정한다. 확대나 키보드 때문에 공간이 부족하면 주요 조작 접근을 우선하고 N줄·높이 상한은 프로젝트의 검증된 권장값으로 둔다. 하드웨어 키보드·키보드 탐색에서도 탭 없이 입력에 진입할 수 있어야 한다.
- **확인 방법**: 실제 대상 모바일 기기에서 여러 줄 입력·한글 조합 중 본문/입력 내부 스크롤, 화면 회전, 인용 시트 열기·닫기, 편집 재개를 수행한다. 입력·선택·초점 보존과 전송/취소 도달성을 확인하고 글자 확대도 포함한다. ego 검증은 별도로 기록하며, 실기기 없이 가상 키보드 항목을 합격으로 처리하지 않는다.

- 검토 범위는 스킬 본문뿐 아니라 기획서·이 보고서·README·새 참조 파일·커밋에 들어갈 이미지·링크도 포함한다. 완료 뒤 기획서를 삭제해도 Git 기록에서 사라지는 것은 아니다.
- 공개 필터의 대상 경로와 검사 항목을 정의하고, 필터 결과와 문맥 검토를 함께 남긴다. 매칭된 민감 원문은 보고서나 터미널에 재출력하지 않는다. 제3자 캡처 커밋 금지와 자기 프로젝트의 영구 기준 화면 기록은 공개 합성 fixture로 함께 충족할 수 있다.
- 확인 방법: 공개용 변경 후보 전체에서 출처를 분류하고 각 예시가 합성/공개 자료만으로 재현되는지 검토한다. 민감 원본 없이도 규칙을 이해하고 적용할 수 있으면 통과한다. 이번 검토는 비공개 원본·전체 Git 이력의 무노출을 증명하지 않았다.

## 지휘 세션에 제안하는 반영 순서

S1에서 위 세 반례의 수용/기각과 이유를 기록한 뒤 적용 범위·시안 비교 축·대화형 패턴의 지위를 먼저 확정한다. S2의 일반 규칙과 비공개 프로젝트 검증 의존 부분을 분리하고, S3에는 가상 채팅 설계 한 건 외에 위 작은 수정·새 방향 선택·입력 지속성 시나리오를 포함한다. 이번 워커는 지정 보고서만 작성했으며 원본 규칙 수정·커밋·push는 수행하지 않았다.
