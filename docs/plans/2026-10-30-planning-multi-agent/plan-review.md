## 중요한 반례

### 1. 필수 반박을 못 했다는 알림 뒤 구현으로 넘어갈 수 있는 경로

- **상황:** T2 또는 설계가 불확실한 기획이어서 다른 모델 반박 대상이지만, 사용할 다른 모델이 없는 환경이다.
- **어떻게 깨지는지:** 기획서는 다른 모델을 확인하지 못하면 완료라고 하지 말라고 정했으나, 불가능한 경우에는 “진행 여부를 사용자에게 알린다”까지만 정했다. 기존 단일 세션 대체 절차는 직접 구현을 허용한다. 따라서 반박을 미완료로 기록하면서도 구현을 진행하는 경로를 명시적으로 막지 못한다. 이는 구현 전에 반박한다는 목적과 맞지 않는다. 실제 실행 실패를 주장하는 것이 아니라, 두 문서에 정의된 대체 경로의 선행 조건 누락이다.
- **근거:** `docs/plans/2026-10-30-planning-multi-agent.md:30–33`(반박 대상·모델 확인·반영), 같은 파일 `:68`(불가능 환경은 알림), `skills/harness/SKILL.md:44–47`(단일 세션 직접 구현). 현재 완료 기준 `docs/plans/2026-10-30-planning-multi-agent.md:84`는 반박을 “요구”하는지까지만 확인한다.
- **확인 방법:** 위 네 구간을 대조한다. 구현 후 새 세션에 “다른 모델을 사용할 수 없는 환경이며 설계가 불확실한 T1 작업을 구현까지 요청받았다”는 조건을 주고, 구현 착수 여부와 반박 상태를 확인한다. 이 검토에서는 새 구현 세션을 실행하지 않았다.
- **제안:** 필수 반박 대상에는 “다른 모델의 반박과 수용/기각 기록이 끝나기 전 구현하지 않는다”를 명시한다. 불가능하면 진행을 보류하고 사용자에게 예외 여부를 묻되, 예외로 진행한 사실과 반박 미완료 상태를 남긴다. 작고 명확해서 처음부터 반박 대상이 아닌 작업은 이 차단 대상에서 제외한다.

### 2. T2 적용까지 승인된 요청에서 기존 적용 단계가 다시 승인을 요구함

- **상황:** 사용자가 대상과 범위를 지정해 T2 변경의 구현·적용까지 명시적으로 승인했고, 적용 전 미리보기도 그 범위와 일치한다.
- **어떻게 깨지는지:** 새 설계는 기존 승인 범위를 존중하고 새 외부 영향 등에 다시 승인받는다고 하지만, 기존 harness 6단계는 미리보기 다음에 명시적 승인과 게이트 해제를 요구한다. 계획에는 새 승인 소절을 추가한다는 설명은 있어도 이 기존 적용 단계를 어떻게 바꿀지, 여기서 말하는 승인이 앞서 받은 승인으로 충족되는지 명확하지 않다. T1의 “바로 구현할까요?”만 없애고 T2의 재질문은 남아도 현재 완료 기준을 통과할 수 있다.
- **근거:** `docs/plans/2026-10-30-planning-multi-agent.md:50–54`(승인 범위와 재승인), 같은 파일 `:83–86`(완료 기준에 T2 승인 분기 없음), `skills/harness/SKILL.md:35–37`(계획 승인), 같은 파일 `:96–100`(미리보기 후 적용 승인). `scripts/guard.py:18` 및 `:159–165`의 별도 명령 확인도 유지 대상이다.
- **확인 방법:** 위 승인 구간을 나란히 읽고 “구현만 승인”과 “구현·적용까지 승인” 두 경우에 필요한 다음 행동을 각각 써 본다. guard는 명령을 실행하지 않고 JSON 입력만 전달해 확인했다. 현재 worktree에서 `python3 -B scripts/guard.py`에 `{"tool_input":{"command":"cdk deploy"}}`를 입력하면 `permissionDecision: ask`를 출력한다. 실제 배포는 실행하지 않았다.
- **제안:** harness 6단계도 변경 대상으로 명시하고, 적용까지 승인됐으며 미리보기가 일치하면 기존 승인을 이어 쓰는지 정확히 적는다. 구현만 승인된 경우에는 적용 승인을 받도록 구분한다. 대화에서 중복 승인을 줄이는 규칙과 guard의 실행 확인은 별개라고 적어 기존 guard 보호 범위를 유지한다. 이 두 승인 분기를 완료 기준에 넣는다.

### 3. init의 프로필 등급 줄만 바꾸면 일반 push의 상충 지시가 남음

- **상황:** 배포가 아닌 저장소에서 init을 진행하며 사용자가 첫 커밋을 승인했다.

- **근거:** `docs/plans/2026-10-30-planning-multi-agent.md:24`(init 변경 범위), 같은 파일 `:55`(일반 push 승인 규칙) 및 `:85`(문구 중심 완료 기준). `skills/init/SKILL.md:12–13`(push는 반드시 확인), `:64` 및 `:71`(커밋 승인으로 push), `:97–106`(push하지 않음과 첫 커밋). `scripts/guard.py:84–97`은 배포 아님 프로필의 일반 push를 허용한다.
- **확인 방법:** `rg -n 'push|첫 커밋|작업 등급' skills/init/SKILL.md`로 상충하는 지시를 함께 확인한다. 현재 worktree의 `cwd`와 `{"tool_input":{"command":"git push"}}`를 `python3 -B scripts/guard.py`에 JSON으로 넣었을 때 출력이 없음을 확인했다. 이는 훅 판정만 확인한 것으로 실제 push는 실행하지 않았다.
- **제안:** init 수정 범위에 위 상충 문장의 정리도 포함한다. 초기화에는 별도의 push 보류가 의도된 것이라면 공통 규칙의 명시적 예외로 적고, 아니라면 공통 승인 규칙을 참조하도록 바꾼다. guard 코드는 변경하지 않는다.
