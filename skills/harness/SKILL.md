# harness: 요청에서 완료까지

사용자는 /kit 명령을 외우지 않는다. "이 기능 만들어줘", "이 오류 고쳐줘", "이어서 해줘"를 받으면 이 스킬이 의도를 읽고 절차를 골라 계획·구현·검증·기록·(정책이 허용하면) 배포까지 잇는다.
**규칙은 이 파일의 "공통 규칙" 한 곳**에 있고, 상세 절차는 각 스킬에 있다. 다른 스킬·프로필·훅은 정의를 다시 쓰지 않고 여기를 가리킨다.
프로필에 예전 "작업 규칙" 문장이 남아 있으면 이 공통 규칙이 우선한다. 사실 줄(빌드·테스트·배포·push·자동 배포)은 프로필을 따른다.
Orca 작업 지시(Task·Dispatch ID)를 받은 워커는 이 절차를 다시 시작하지 않고 지시 범위만 한다. 사용자에게 하는 질문과 보고는 **한국어**로 한다.

## 의도 → 흐름

| 요청 (예) | 흐름 | 읽을 파일 |
|---|---|---|
| 질문 ("GIL이 뭐야?", "이 함수 뭐 해?") | 답만 한다. 파일·기획서·커밋을 만들지 않는다 | 없음 |
| 기능·수정 ("만들어줘", "바꿔줘") | 등급(1) → T1 이상은 계획(2) → 실행(3) → 검증(5) → 마무리(7) | `<base directory>/../plan/SKILL.md` |
| 오류 ("안 돼", 로그 붙여넣기) | 읽기 전용 진단 먼저 → 원인·해법이 분명하면 그 등급으로, 아니면 조사 워커 | 분류 뒤 plan |
| 이어서·어디까지 ("이어서 해줘", "어디까지 했지?") | 이어서(8). "어디까지"는 보고만 | 없음 |
| 프로젝트 구조·개발 순서 ("구조 잡아줘") | 프로젝트 설계 `docs/plans/project.md` | plan의 "프로젝트 설계" |
| 화면 ("화면 만들어줘", "디자인 고쳐줘") | design 절차 + 공통 규칙 | `<base directory>/../design/SKILL.md` |
| 점검 ("점검해줘", "리뷰해줘") | 보고 먼저, 수정은 승인 뒤 | `<base directory>/../check/SKILL.md` |
| 배포 ("배포해줘", "릴리즈") | 공통 규칙 "push와 배포" → release 절차 | `<base directory>/../release/SKILL.md` |
| 블로그 ("블로그로 쓰자") | 작성·검수까지. 발행 승인은 공통 규칙 "push와 배포" | `<base directory>/../blog/SKILL.md` |
| kit 개선 (다른 레포에서 "kit 이거 고치고 싶다") | 이슈만 남기고 하던 일로 | `<base directory>/../feedback/SKILL.md` |

- 질문인지 작업인지 애매하면 읽기 전용 확인(코드·설정 읽기)부터 하고, 바꾸기 전에 묻는다.
- 커밋은 `<base directory>/../commit/SKILL.md`. 작업에 필요한 사실(빌드·테스트·배포·push)이 프로필·README에 없으면 `<base directory>/../init/SKILL.md`의 보완 절차로 그 줄만 채운다. 사용자가 원하지 않으면 프로필 없이 진행한다 (push·배포는 묻는 쪽).
- **경로로 읽을 때의 계약**: plan·init·release는 Skill 목록에 없으므로 Read로 읽는다. 읽은 SKILL.md가 있는 폴더를 그 스킬의 base directory로 써서 `<그 폴더>/../../scripts/...`를 푼다. 여기서 파악한 요청을 그 스킬의 인자로 보고 같은 질문(무엇을 만들지 등)을 다시 하지 않는다.

## 공통 규칙

### 1. 등급과 배치

| 등급 | 예 | 절차 |
|---|---|---|
| **T0** | 질문, 문서 오타, 원인과 해법이 분명한 작은 수정 | 바로 처리. 계획·워커 없음 |
| **T1** | 기능 추가, 버그 수정, 리팩터링, 테스트 | 계획(2) + 구현 + **독립 검증**(5) |
| **T2** | 배포, 배포가 되는 push, AWS·IAM·시크릿, 인프라, 마이그레이션, 확정된 설계 변경, 데이터 삭제 | T1 + **실행 전 명시적 계획 승인** + 적용 전 읽기 전용 미리보기(6). 자동 배포 정책 안의 배포는 아래 "push와 배포" |

- 애매하면 높은 등급으로. **등급은 영향 범위로** 정한다 (권한 두 줄도 배포가 따르면 T2). 분류는 한 줄로 알린다: `등급: T1 (버그 수정, 원인 불명 → 조사 워커 먼저)`
- **배치는 불확실성**(원인·해법이 분명한가)과 **분리 가능성**(겹치지 않는 파일·모듈로 나뉘는가)으로 정한다. 줄 수·파일 수는 근거가 아니다. 직접 고쳐도 승인·미리보기·검증은 빼지 않는다.

  | 상황 | 배치 |
  |---|---|
  | 작고 원인·해법이 분명 | 지휘 세션이 직접 (T1이면 검증은 다른 워커) |
  | 작아도 원인이 불명 | 읽기 전용 조사 워커 → 결과로 다시 분류 |
  | 겹치지 않는 모듈 여러 개 | 병렬 Coder(각자 하위 worktree) + 통합 검증 |
  | 설계가 불확실하거나 영향이 큼 | 다른 모델 기획 반박(2) → 구현 → 독립 검증(5) |

- 원인을 찾는 읽기 전용 진단(로그·코드·설정 읽기)은 등급과 상관없이 먼저 해도 된다.
- **다른 모델의 의견·검토**(GPT·Codex, agy 등)는 등급과 상관없이 3단계의 워커로 띄운다. Orca가 있으면 `worker-start --agent codex|antigravity` 탭으로 띄우고 의견은 완료 증거에 정한 보고서 파일로 받는다. `codex exec`, `agy -p`처럼 화면에 안 보이는 호출은 Orca가 없을 때만 쓴다 (사용자가 과정을 보고 싶어 한다).

### 승인
- **계획 승인** (실행 전): 무엇을 어디까지 할지. T2는 명시적 승인 전에는 실행하지 않는다. 승인되면 `status: approved`. 처음 요청이나 승인에 구현이 들어 있으면 "바로 구현할까요?"를 다시 묻지 않는다. 기획만 요청했으면 기획서까지 하고 멈춘다.
- **미리보기** (T2 적용 전, 6): 실제로 바뀌는 것이 승인 범위와 같은지 확인하는 단계다. 계획 승인을 대신하지 않는다.
- **다시 승인받는 경우**: 승인 범위 밖 파일·시스템, 새 외부 영향(배포, 배포가 되는 push, 삭제, 권한·시크릿), 미리보기의 예상 밖 변경. **다시 묻지 않는 경우**: 승인된 구현 안에서 검증이 찾은 결함의 수정·재검증.
- **점검 요청**: 사용자가 따로 "점검해줘"라고 하면 check대로 보고 먼저, 수정은 승인 뒤. 5단계에서 check를 쓰면 결과는 지휘 세션이 받고 범위 안 결함은 Coder에게 다시 맡긴다.

### push와 배포
- **일반 push**: 프로필 push 줄이 `배포 아님`이면 커밋 요청·승인이 push 승인을 겸한다. 줄이 없거나 `배포`면 push는 배포로 본다 (T2, 또는 아래 자동 배포). 강제·삭제 push는 항상 따로 확인한다.
- **정책이 다루지 않는 것**: 태그 push, 릴리즈 생성(`gh release create`), 파일 전달은 push 줄·자동 배포 정책과 상관없이 매번 직접 확인한다.
- **블로그 발행**(tech-blog main 병합·push): 자동 배포 정책에 넣지 않고 **글마다** 명시 승인을 받는다. "글 써줘"는 작성·검수까지이고 발행 승인이 아니다. 승인을 묻는 방법은 blog K6.
- **자동 배포**: 프로필에 정책 줄이 있고 이번 변경이 정책 안이면 **계획 승인이 배포 승인을 겸한다**. 줄 형식은 init, 명령은 release. 조건 (guard가 push 때 같은 것을 대조한다):
  1. push가 정확히 `git push <원격> <40자리 SHA>:refs/heads/<브랜치>` 하나이고 원격·브랜치가 정책 `대상`과 같다 (`main` 같은 움직이는 이름은 묻는다)
  2. push URL과 fetch URL이 같고, `ls-remote`로 읽은 원격 base에서 그 SHA로 fast-forward다
  3. base와 SHA의 CLAUDE.md 정책이 둘 다 허용이고 같다 (정책을 넓히거나 처음 넣는 push는 사람이 승인)
  4. 그 SHA에서 `deploy_gate.py verify`가 통과한 기록이 있다 (그 SHA의 깨끗한 임시 checkout에서 실행, 검증 명령이 추적 파일을 바꾸면 실패. 병합으로 SHA가 바뀌면 최종 SHA에서 다시)
  5. 바뀐 파일이 `제외`에 걸리지 않고 diff에 시크릿 패턴이 없다
- **IAM·시크릿·인프라·마이그레이션·데이터 삭제는 정책과 상관없이 T2 명시 승인**이다. 이 분류는 guard가 증명하지 못하므로 harness가 판단한다 (`제외` glob은 보조). 계획을 보일 때 `자동 배포: 정책 안` 또는 `자동 배포: 정책 밖 (이유)`를 한 줄로 알린다.
- guard(위험 명령 확인 훅)는 best-effort 확인이지 권한 경계가 아니다. 확인 창은 대화 승인과 별개로 뜬다. 확인 창·자동 모드·훅이 막으면 **우회하지 않고** 명령을 보여 줘 사용자가 `! <명령>`으로 실행하게 한다.

### 완료 판정과 기록
- **완료 = 사용자가 보게 될 결과**까지 확인한 것 (예: 배포 사이트에서 보고서 1건 생성 성공). 배포는 **push한 SHA에 묶인 증거**: 그 SHA의 배포 실행 성공 + 핵심 기능 결과 (`deploy_gate.py confirm` exit 0 또는 release의 방식별 확인). push 성공, "최근 실행 성공", HTTP 200만으로 완료라고 하지 않는다.
- 배포 실패면 멈추고 반영된 SHA·실행 id·롤백 방법을 보고한다. 자동 롤백은 하지 않는다 (되돌림 커밋도 배포라 승인을 받는다).
- **기록은 기획서와 커밋뿐이다.** 질문은 아무 파일도 만들지 않는다. T0 수정은 커밋 메시지가 기록이다. T1 이상은 기획서의 결정 & 이유, 단계 체크박스 + 결과 한 줄, `## 남은 일`에 적고, 기획 커밋부터 그 작업의 **모든 커밋 본문에 `Refs: docs/plans/<파일>`** (필수). 커밋 목록은 적지 않는다 (`git log --grep "Refs: docs/plans/<파일>"`). 기획서 갱신은 각 단계의 작업 커밋에 같이 넣고(체크박스 `[x]` + 결과 한 줄), 작업 로그·메모를 따로 만들지 않는다. 배운 것(왜 그렇게 했나, 무엇이 틀렸었나)은 결정 & 이유와 단계 결과에 쓴다.
- **끝난 기획서는 지운다** (사용자 결정, 2026-10-30). 삭제 커밋의 tree에는 파일이 없으므로 최종 상태는 그 **직전 커밋**에 있어야 한다:
  1. 마지막 작업 커밋에 기획서의 `status: done`(그만두면 `abandoned` + 이유), 마지막 단계 결과, `## 남은 일`을 같이 넣는다. 커밋이 하나뿐인 작은 작업도 이 커밋을 먼저 한다.
  2. 바로 이어서 삭제 커밋 하나: 기획서와 보고서 폴더(`docs/plans/<이름>/`)를 `git rm`, 메시지 `docs(plan): <slug> 완료, 기획서 삭제`, 본문에 Refs + 결과 한 줄 (+ 사용자만 할 수 있는 남은 확인).
- kit가 이어서 할 일이 남았으면 `done`이 아니다 (`in-progress`, `## 남은 일`에). `docs/plans/project.md`는 지우지 않고 끝난 항목을 `완료 <커밋>`으로 바꾼다.
- 지운 기획서 찾기: `git log --all --format=%h -- docs/plans/<파일>` → `git show <삭제 커밋>^:docs/plans/<파일>` (위 순서를 지켰으면 `done` 상태와 결과가 보인다).

## 절차

### 2. 계획 (Planner, T1 이상)
- 파일 `docs/plans/YYYY-MM-DD-<영어-slug>.md`, 형식은 plan의 "4. 기획서 작성". 질문은 필요한 것만 한다.
- front matter에 `tier`, 작업 단계에 **담당과 확인 가능한 완료 조건**: `- [ ] S1. 무엇을 — Coder — \`npm test\` 통과, 변경은 src/auth/ 안에서만`. 완료 조건은 사용자가 보게 될 결과까지 쓴다.
- T2는 "승인 필요"에 바꾸는 것, 미리보기 명령(`cdk diff`, `terraform plan`, `--dry-run`), 롤백 방법. 자동 배포 대상이면 정책 안/밖 한 줄.
- 사용자에게 목표·단계·승인 필요 항목을 짧게 보여 준다 (반박 대상이면 반박을 거친 계획). 수정이 3회를 넘기면 범위를 줄이자고 제안한다.

**기획 반박** (다른 모델)
- **대상**: 불확실성이 높거나(확인 안 한 가정, 설계 갈림길, 원인 불명) 영향이 큰(T2, 여러 프로젝트에 퍼지는 규칙·훅) 기획. 작고 명확한 T1은 하지 않는다.
- **검토자**: 작성자와 **다른 실제 모델** (Claude가 썼으면 Codex·agy 워커). 같은 모델에 역할 이름만 바꾼 검토는 반박이 아니다. 실행 모델은 실행 중에 `orca orchestration worker-show --dispatch <id> --json`의 `projection.provider.model` → 없으면 워커가 보고한 모델 순으로 확인해 기획서에 적는다 (`launch.effective.model`은 null일 수 있고 projection은 정산 뒤 빈다). 둘 다 없으면 "미확인"으로 적고 완료라고 하지 않는다.
- **묻는 것**: (1) 사용자 문제를 정말 해결하는가 (2) 더 작은 해법 (3) 확인하지 않은 가정 (4) 완료 기준은 통과해도 실사용에서 깨지는 반례. 보고서에 **중요한 반례 최대 3개 + 각각 확인 방법**.
- **반영**: 작성자가 "기획 반박" 섹션에 검토자(agent·model·ID)와 반례별 수용/기각 + 이유를 적고 계획을 고친다. 그 기록 전에는 구현하지 않는다. 다른 모델을 쓸 수 없으면 멈추고 예외로 진행할지 묻는다 (예외면 "다른 모델 반박 미완료(사유)").

### 3. 실행 (Supervisor)
무엇을 맡길지(단계, 범위, 완료 조건, 금지)를 정하고, 워커를 띄우고 주고받고 정리하는 방법은 실행 도구의 규칙을 따른다. **Validator는 Coder와 다른 워커**로 한다 (가능하면 다른 모델).

**워커 고르기** (위에서부터 가능한 것)
1. **Orca** (`command -v orca`): `orca skills get orchestration` 안내서를 그대로 따른다 (대기·재시도·정리). 사용자가 미리 허락했으므로 확인 없이 띄우고, 아래 배치를 계획에 적는다.
2. **서브에이전트**: Coder는 `isolation: "worktree"`, Validator는 새 서브에이전트.
3. **단일 세션**: 직접 구현하고 검증은 check 절차로. 독립성이 약하다는 점을 보고에 적는다.

**Orca 배치와 보드**
- **작업 하나 = worktree 하나 = 보드 카드 하나.** 세션이 본체(main)에 있거나 지금 worktree에 끝나지 않은 다른 작업이 있으면 새 worktree(`orca worktree create --repo id:<repoId> --name <기획서 slug> --no-parent --json`). 거절하면 지금 worktree에서 하고 카드에 작업이 섞인다고 알린다. 대상은 그 안에 있으면 `current`, 아니면 create가 돌려준 `id:<repoId>::<path>`를 계속 쓴다.
- **역할 하나 = 탭 하나**: 필요한 역할만 그 worktree에 `worker-start`로 차례로 (Validator는 Coder의 커밋을 같은 폴더에서 검사).
- **같은 시간에 파일을 고치는 워커가 둘 이상**일 때만 각자 하위 worktree(`worker-start --worktree new-child`, 밖이면 `orca worktree create ... --parent-worktree <대상> --base-branch <작업 브랜치>`)에 두고 담당 범위를 나눈다. 끝나면 작업 worktree로 병합한다. 따로 병합·배포할 단위면 처음부터 별도 기획서로. git이 아닌 폴더는 같은 폴더에서 차례로.
- **카드**: 단계가 바뀔 때 `orca worktree set --worktree <대상> --workspace-status <상태> --comment "<지금 하는 일>"` (사용자 확인 대기면 `--unread`). 기획·승인 대기 `todo` → Coder `in-progress` → Validator·미리보기 승인 대기 `in-review` → 검증·적용·병합(push 승인 시 push) 끝 `completed`. 재작업은 `in-progress`로, 막히면 상태는 두고 comment에 이유.

**작업 지시** (Orca Task spec과 같은 5항목. 워커에게는 대화가 아니라 이것만 준다)
```text
대상: <계획 단계 id, 다룰 파일·컴포넌트·환경>
변경: <만들어야 할 결과>
제약: <지킬 규칙>. push, 배포, AWS 쓰기, 시크릿 출력 금지. 막히면 추측하지 말고 질문으로 올린다.
담당 범위: <이 워커가 수정해도 되는 파일·폴더>
완료 증거: <실행할 명령과 기대 결과>
```
Claude가 아닌 에이전트는 CLAUDE.md를 읽지 않는다. `AGENTS.md`가 없으면 만들자고 제안하고, 작업 지시에 제약을 그대로 붙인다.

### 4. 워커 보고
- **Orca**: `worker_done` (3문장 요약, `--outcome`, `--files-modified`, 긴 출력은 `--report-path`). 실행한 검사와 결과, 남은 위험을 넣게 한다.
- **서브에이전트·단일 세션**: `STATUS: SUCCESS|PARTIAL|ERROR` / `DONE` / `CHANGED` / `CHECKS: 명령 → 결과` / `NOT DONE / RISKS`, 150단어 이내.
- 실패는 오류 출력과 함께 다시 맡기고, 두 번 실패하면 사용자에게 올린다.

### 5. 검증 (Validator)
Coder의 보고를 믿지 않고 **처음부터 다시** 확인한다.
- 프로필의 빌드·테스트 재실행 (check의 2·3단계), diff가 담당 범위 안인지 (`git diff --stat <base>...HEAD`)
- 시크릿: `git diff <base>...HEAD | grep -nE 'AKIA|secret|api[_-]?key|BEGIN .*PRIVATE'`. 숫자·집계는 다시 계산한다
- 권한 변경은 실제 실행 역할로 확인한다 (관리자 키 로컬 테스트는 누락을 가린다. AWS면 `aws iam simulate-principal-policy`로 쓰는 액션 전부)
- **독립 실패 시나리오**: 완료 기준에서 중요한 실패·경계 시나리오 1~3개를 직접 고른다 (Coder의 시나리오를 그대로 쓰지 않고, 구현을 베낀 테스트를 만들지 않는다). 문서 변경이면 새 세션에서 적용해 보거나 문서끼리 대조한다. 시나리오마다 선택 이유, 재현 명령, 실제 결과, 미검증 사항을 적는다.

### 6. T2 적용
1. 미리보기를 실행하고 바뀌는 것만 요약한다. 예상 밖 변경이 있으면 멈추고 보여 준다.
2. 적용까지 승인받았고 미리보기가 그 범위와 같으면 다시 묻지 않고 적용한다. 구현만 승인했으면 미리보기를 보여 주고 적용 승인을 받는다. Orca로 여러 단계를 돌리면 그 단계를 `gate-create`로 막아 두고 승인받으면 푼다.
3. 적용 후 완료 판정(공통 규칙)까지 확인한다. 사용자만 할 수 있는 확인은 `## 남은 일`에 남긴다.

### 7. 마무리 (Tracker)
- 검증을 통과한 워커 브랜치를 병합한다. 커밋은 commit 절차, 본문에 `Refs: docs/plans/<파일>`.
- 체크박스 `[x]`와 단계 결과 한 줄은 그 단계의 커밋에 같이 넣는다. 모두 끝났으면 공통 규칙 "완료 판정과 기록"대로 `done` 갱신 커밋 → 삭제 커밋.
- 정리: Orca 워커는 안내서의 완료 정산을 따른다 (`task-update`로 다시 바꾸지 않는다). 병합이 끝난 하위 worktree와 `completed` 작업 worktree는 사용자 확인 후 `orca worktree rm --worktree <selector>` (지휘 세션이 그 안에 있으면 지워 달라고 안내). Orca 밖 worktree는 `git worktree remove`, `git branch -d`. 남은 worktree·탭(사용자 소유로 바뀐 것 등)은 목록으로 보고한다.

### 8. 이어서
- **kit 판정과 상관없이** 현재 git 루트에서 재개 목록을 얻는다 (프로필 없이 시작한 작업도 이어진다):
  `sh <base directory>/../../scripts/py.sh <base directory>/../../scripts/plans.py` (기계용은 `--json`)
- 모든 worktree의 진행 중 기획서가 나온다. 끝난 작업(어느 복사본이 `done`·`abandoned`이거나 기본 브랜치에서 지워짐)은 이미 빠져 있다. **이 활성 목록만 보고하고, 끝난·지운 기획서는 읽거나 보고하지 않는다.** 복사본끼리 다르면 "충돌"로 표시된다. 하나면 바로, 여럿이거나 충돌·"상태 확인 필요"면 사용자가 고르게 한다.
- `--all`(5개 제한 없이 + 끝난 작업의 오래된 복사본 진단)은 사용자가 그걸 묻거나 충돌·"상태 확인 필요"를 풀 때만 쓴다.
- 고른 worktree에서 기획서 체크박스, `git log --grep "Refs: docs/plans/<파일>"`, `git status`, 실제 파일을 대조해 **첫 미완료 단계부터** 한다. 끝난 단계는 다시 하지 않는다. "어디까지 했어?"면 대조 결과만 보고한다.
- 목록이 비면 최근 커밋과 `git status`로 상황을 요약하고 무엇을 이어 할지 묻는다.
