# 대화형 패턴

[작업 화면 유형](system.md#화면-유형)의 하위 패턴이다. 독립된 화면 유형이 아니다. 작업 화면의 공통 규칙과 [부품별 동작 계약](system.md#부품별-동작-계약)은 그대로 적용하고, 이 문서는 대화형에만 생기는 규칙을 더한다.

## 적용 범위

- 읽는 때: 사용자가 글로 묻고 시스템이 이어서 답하는 화면(채팅, 질의응답, 에이전트 실행)을 만들거나 고칠 때.
- 읽지 않는 때: 입력창 하나가 있는 일반 폼, 댓글 목록, 검색창만 있는 화면.
- 이 문서는 세 층이다. **동작 계약**은 의무다. **배치 예시**와 수치는 프로젝트가 고르고 프로필에 고정한다. **음성 자리**는 아직 구현 규칙이 아니다.
- 근거: 한 비공개 프로젝트(도메인 전문가용 리서치 에이전트)의 시안과 독립 검증. 정적 매트릭스(14크기×17상태)는 가로 넘침·44px 미달이 모두 0이었고, 실패는 전부 **연속 조작**에서 나왔다. 그래서 검증은 캡처보다 조작 순서를 본다.
- 검증 수준: ego 에뮬레이션 검증, 실기기 미확인. 실기기 iOS Safari·Android 가상 키보드, 한글 IME 조합, 터치 선택 손잡이는 확인하지 않았다.

## 동작 계약(의무)

| 계약 | 실행 문장 | 확인 방법(ego) |
|---|---|---|
| 초안·커서·선택 보존 | 초안·캐럿·선택 범위는 접기·펼치기·화면 회전·패널 전환 뒤에도 그대로다. 편집 중(초점이 있거나 초안이 있음)에는 자동으로 접지 않는다. 화면을 열 때 입력창에 자동 초점을 주지 않는다 | 여러 줄 입력 → 선택 범위 지정 → 근거 열고 닫기·폭 변경 → `value`, `selectionStart/End`, `selectionDirection`, `document.activeElement`가 전과 같은지 측정. 첫 로드 직후 `activeElement`가 입력창이 아닌지 |
| 읽는 위치 유지 | 사용자가 위로 올려 읽는 중이면 새 이벤트가 와도 스크롤을 옮기지 않는다. 맨 아래에 있을 때만 따라간다 | 답이 흐르는 중 위로 스크롤 → 이벤트 몇 개 수신 → 대화 영역 `scrollTop`과 읽던 요소의 rect가 그대로인지 |
| 근거 도달과 복귀 | 모든 출처·근거는 터치와 키보드로 열린다. 닫으면 초점은 연 칩으로, 스크롤은 읽던 위치로 돌아온다 | 칩 터치로 열기 → 내용 끝까지 이동 → 닫기 → `activeElement`가 그 칩이고 대화 `scrollTop`이 같은지. 키보드 Enter/Escape도 따로 |
| 중지·재연결 무결 | 같은 이벤트를 다시 받아도 논리 ID로 한 번만 그린다. 중지 뒤 늦게 온 이벤트는 상태를 되돌리지 않는다. 중지까지 받은 부분 결과는 "중지됨" 표시와 함께 남긴다 | fixture로 같은 ID 이벤트 재전송 → DOM 항목 수. 중지 → 늦은 이벤트 주입 → 상태 표시가 "중지됨"으로 남는지 |
| 대기·미지원·실패 구분 | 기다리는 중, 이 기기·설정에서 못 함, 시도했지만 실패를 서로 다른 글과 상태로 보인다. 색만으로 구분하지 않는다 | 세 상태를 각각 만들어 글자·접근 가능한 이름이 다른지 |
| 진행은 실제 이벤트만 | 진행 줄·경과 시간·단계 이름은 실제로 받은 이벤트에서만 만든다. 받지 않은 단계를 미리 보여 주지 않는다 | 미리 만든 상태가 아니라 **실제로 보낸 흐름**에서 경과 시간이 흐르고 단계가 이벤트 순서와 같은지 |
| 조작 영역과 확대 우선 | 44px 조작 영역과 200% 글자 대응이 높이 상한보다 우선한다. 높이가 모자라면 글자를 줄이거나 내용을 자르지 않고 배치를 바꾼다 | 200% 글자·폰 가로에서 `measureUI`의 좁은 조작영역 후보 0, 줄 겹침 없음, 입력·전송·중지에 도달 |

## 구현에서 자주 깨지는 곳

검증에서 실제로 나온 실패 유형을 일반화했다. 증상 → 원인 → 규칙 → 확인 순서다. 위 계약을 지키려다 생기는 구현 함정이며, 계약을 대신하지 않는다.

1. **탭 하나가 두 번 먹힘**
   - 증상: 접힌 입력을 탭했더니 펼쳐지면서 초점이 새로 나타난 도구 버튼으로 간다.
   - 원인: pointerdown에서 펼쳐 레이아웃이 먼저 바뀌고, 같은 탭의 남은 touchend/click이 새 버튼 위에 떨어진다.
   - 규칙: 펼침은 focus에서만 한다. 그 탭의 남은 click만 한 번 버리고, 새 pointerdown/touchstart/keydown이 오면 즉시 해제한다. 시간 창(예: 0.5초) 필터는 쓰지 않는다. 곧이은 정당한 별개 탭을 삼킨다.
   - 확인: 실제 터치 이벤트로 접힌 입력 탭 → `activeElement`가 입력창. 이어서 바로 도구 버튼을 탭 → 그 버튼이 동작.
2. **확대하면 줄이 겹침**
   - 원인: 고정 px line-height.
   - 규칙: line-height는 단위 없이 쓴다. 입력 높이·최대 줄 수는 계산된 line-height와 padding에서 구한다.
   - 확인: 200% 글자에서 줄마다 rect가 겹치지 않는지.
3. **한 줄 미리보기에 다음 줄 조각이 비침**
   - 상황: 초안이 있는 접힌 입력을 사용자가 읽으려고 스크롤한 상태.
   - 규칙: 내부 스크롤을 줄 단위로 스냅하고, padding 띠는 clip-path로 자른다.
   - 확인: 접힌 상태에서 내부 스크롤 후 캡처를 확대해 위·아래 줄 조각이 없는지.
4. **입력 중 캐럿 줄이 가려짐**
   - 원인: 줄 스냅·자동 높이 뒤 scrollTop이 캐럿을 따라가지 않는다.
   - 규칙: 입력·캐럿 이동·높이 변화 뒤 캐럿 줄이 보이게 scrollTop을 보정한다. 사용자가 입력창 안을 직접 민 스크롤은 되돌리지 않는다. 역방향 선택(Shift+↑)에서는 활성 끝이 selectionStart다. selectionEnd만 보면 틀린다.
   - 확인: 최대 줄 수를 넘게 입력 → 맨 끝·중간에서 캐럿 이동 → Shift+↑ 선택 → 매번 캐럿 줄이 입력창 안에 보이는지. 직접 스크롤한 뒤에는 위치가 유지되는지.
5. **전환 조건이 두 곳**
   - 증상: 근거 패널이 특정 폭 구간에서만 아래로 떨어진다.
   - 원인: 전환을 가독 폭으로 정의했는데, 구현은 고정 폭 미디어 쿼리 안에만 있었다.
   - 규칙: 옆 패널/시트 전환 조건은 한 곳(가독 폭 계산)에서만 정한다.
   - 확인: 계산한 경계 폭 ±1px에서 실제 배치를 측정한다. 미디어 쿼리 경계도 소스에서 찾아 따로 본다.
6. **키보드로 연 메뉴에 못 들어감**
   - 규칙: 열면 첫 항목에 초점을 준다. 좁은 폭 메뉴 안에서는 Tab이 순환한다. Escape는 연 버튼으로 초점을 돌린다.
   - 확인: Enter로 열기 → Tab 여러 번 → Escape 각각 뒤의 `activeElement`.
7. **단축키가 특정 초점에서만 동작**
   - 증상: 입력창으로 가는 `/` 같은 단축키가 body 초점일 때만 된다.
   - 규칙: 전역으로 받는다. 단 편집 요소에 초점이 있을 때, 시트·좁은 폭 메뉴가 열렸을 때, 보조키가 눌렸을 때, 음성 중일 때는 제외한다.
   - 확인: 칩·버튼에 초점을 둔 채 누르기, 입력 중·시트 열림에서 누르기를 각각.
8. **경과 시간이 실제 흐름에서 멈춤**
   - 증상: "진행 중 N초"가 미리 만든 상태에서는 흐르지만 실제로 보낸 흐름에서 0초에 멈춘다.
   - 규칙: 진행 표시는 실제 보낸 흐름에서 검증한다.
   - 확인: 입력 → 전송 → 몇 초 뒤 값이 늘었는지.
9. **아이콘 버튼 크기가 화면마다 다름**
   - 원인: 아이콘 버튼 글자 크기가 부모를 상속한다.
   - 규칙: 토큰으로 고정한다. [한 디자이너 점검](system.md#한-디자이너-점검)의 계산값 대조에 포함한다.
   - 확인: 화면마다 같은 역할 아이콘 버튼의 `getComputedStyle` 글자 크기·rect.

## 배치 예시(프로젝트가 고른다)

아래 값은 **한 프로젝트에서 검증한 권장값**이다. 다른 프로젝트는 출발점으로 쓰고, 고른 값을 프로필에 적는다. 그 프로젝트는 [방향 선택](system.md#방향-선택)에서 미니멀(흰 바탕, 강조색 하나)과 문서형 배치(사용자 말만 말풍선, 답은 본문)를 골랐다. 레퍼런스 16곳, 시안 4테마×2배치를 공유 fixture로 비교했다.

| 항목 | 권장값 |
|---|---|
| 모바일 상단 | 얇은 한 줄 바(☰ + 경로). 44px 이상 |
| 입력 기본 상태 | 접힌 한 줄 입력. 44px 이상. 탭할 때만 펼치고 키보드가 올라온다 |
| 폰 세로 높이 예산 | 바 + 접힌 입력이 화면 높이 15% 이하(390×844에서 106px, 12.6%) |
| 폰 가로 높이 예산 | 15%는 44px 조작 두 개만으로도 넘으므로 따로 상한 103px(바 실제 45 = CSS 최소 44 + 1px 선, 접힌 입력 58, 기본 글자 크기 조건). 글자 확대에서는 44px 조작과 확대 대응이 상한보다 우선 |
| 펼친 입력 | 최대 5줄, 넘으면 내부 스크롤 |
| 높이가 모자랄 때 | 순서대로: 바 숨김 → 입력 최대 줄 수 축소(도구 줄 제거) → "키보드 닫고 읽기". 대화 최소 가독 높이 190px. 글자 축소·내용 자르기 금지 |
| 근거 위치 | 본문 최소 가독 폭(한글 약 32자, 560px) + 패널이 함께 들어가면 옆 패널, 아니면 하단 시트(스크림·손잡이). 닫으면 원래 칩·읽던 위치로 |
| 체감 속도 | 보내면 100ms 안에 사용자 말풍선과 접수 표시(실측 1~2ms). 진행 줄은 실제 이벤트만 |
| 이벤트 처리 | 재수신은 논리 ID로 한 번, 중지 뒤 늦은 이벤트 무시, 부분 결과는 "중지됨"과 함께 남김 |

프로필에 고정할 항목:
- 배치: 문서형/말풍선형, 답이 본문인지
- 모바일 바와 접힌 입력의 높이, 폰 세로·가로 높이 상한
- 펼친 입력의 최대 줄 수, 높이가 모자랄 때의 축소 순서, 대화 최소 가독 높이
- 근거 패널/시트 전환 조건(가독 폭 계산식과 값)
- 접수 표시 시간 목표, 진행 표시에 쓰는 이벤트 종류
- 단축키와 제외 조건
- 음성 진입점 여부와 위치
- 허용한 예외와 이유([한 디자이너 점검](system.md#한-디자이너-점검))

## 답 구성

- 답은 결론 한 줄로 시작한다. 그 뒤는 질문에 따라 고른다: 글, 표, 그래프, 도형(흐름·비교). 시각 블록은 의무가 아니다. 글로 충분하면 글만 쓴다.
- 블록 상태
  - 대기: 결론과 글은 먼저 보이고, 블록 자리에 "그리는 중"을 표시한다.
  - 미지원: 이 화면이 그 블록 종류를 그릴 수 없으면 그렇다고 적고 같은 내용을 글이나 표로 보인다.
  - 실패: 실패했다고 적는다. 받은 내용이 있으면 남긴다. 빈 자리나 깨진 그림으로 두지 않는다.
- 출처 칩: 블록 전체의 근거는 블록 머리에, 문장의 근거는 문장 끝에 둔다. 칩은 조작 영역 규칙을 따르고, 여는 곳은 위 근거 위치 규칙을 따른다.
- 진행 표시: 받은 이벤트의 단계 이름과 경과 시간만 보인다. 가짜 진행률 막대를 쓰지 않는다.
- 합성 예: "두 기준을 비교하면?" → 결론 한 줄 + 비교 표 + 행마다 출처 칩. "이 절차가 어떻게 이어지나?" → 결론 한 줄 + 흐름 도형. "이 용어 뜻은?" → 글만.

## 음성을 나중에 붙일 자리

아직 구현 규칙이 아니다. 지금 배치가 음성을 막지 않게 자리만 정한다(미검증).

- 진입점: 입력 줄 안의 버튼 하나. 키보드를 올리지 않고 시작한다. 44px 이상이며, 접힌 입력의 높이 예산에 포함해 계산한다.
- 상태 3종: 듣는 중 / 생각하는 중 / 말하는 중. 각각 글과 접근 가능한 이름으로 구분하고 언제든 중지할 수 있다. 위 대기·미지원·실패 구분을 그대로 적용한다(예: 이 브라우저에서 마이크 미지원).
- 말하는 동안 화면에 남는 것: 받아 적은 사용자 말, 현재 상태, 중지 버튼, 답의 결론 한 줄. 화면을 음성 전용 장면으로 바꾸지 않는다.
- 답의 세 층: 말로 하는 결론(짧게) / 화면의 블록(표·그래프) / 출처 칩. 말은 결론만 하고 상세는 화면에 둔다.
- 음성 중에는 글자 단축키를 받지 않는다(위 실패 유형 7).

## 기기·상황 행

행 정의와 `적용 / 비해당 / 미검증` 규칙의 원본은 [ego 검증의 기기·상황 행](ego-validation.md#기기상황-행)이다. 여기서는 대화형에서 추가로 고를 행만 적는다.

| 추가 행 | 내용 |
|---|---|
| 키보드 가용 높이 fixture 3단계 | viewport 높이를 단계적으로 줄여 높이가 모자랄 때의 축소 순서가 차례로 일어나는지 본다. 3단계 값은 프로필의 높이 예산에서 정한다(예: 여유 있음 / 바 숨김 단계 / "키보드 닫고 읽기" 단계) |
| 근거 패널 경계 폭 ±1px | 가독 폭 계산으로 나온 전환 폭과 그 ±1px에서 옆 패널/시트 |
| 200% 글자 | 입력 줄 겹침, 최대 줄 수 계산, 44px 조작, 높이 상한보다 확대 우선 |
| 폰 가로 | 별도 높이 상한, 펼친 입력과 대화 최소 가독 높이 |

가용 높이 fixture는 **시험 입력**이다. 가상 키보드를 증명하지 않는다. 실제 키보드·IME·선택 손잡이는 실기기로 확인하기 전까지 `미검증`이다.
각 행에서 캡처 외에 위 실패 유형의 연속 조작(탭 → 입력 → 캐럿 이동 → 근거 열고 닫기 → 중지)을 한 번 이상 수행한다.
