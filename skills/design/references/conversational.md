# 대화형 패턴

[작업 화면 유형](system.md#화면-유형)의 하위 패턴이다. 독립된 화면 유형이 아니다. 작업 화면의 공통 규칙과 [부품별 동작 계약](system.md#부품별-동작-계약)은 그대로 적용하고, 이 문서는 대화형에만 생기는 규칙을 더한다.

## 적용 범위

- 읽는 때: 사용자가 글로 묻고 시스템이 이어서 답하는 화면(채팅, 질의응답, 에이전트 실행)을 만들거나 고칠 때.
- 읽지 않는 때: 입력창 하나가 있는 일반 폼, 댓글 목록, 검색창만 있는 화면.
- 이 문서는 세 층이다. **동작 계약**은 의무다. **배치 예시**와 수치는 프로젝트가 고르고 프로필에 고정한다. **음성**은 채택 여부와 자리만 정한다.
- 새 대화 화면은 해당하는 동작 계약과 연속 조작을 모두 검증한다. 작은 수정은 변경 영향이 있는 계약만 본다.
- 근거: 한 비공개 프로젝트(도메인 전문가용 리서치 에이전트)의 시안과 독립 검증. 정적 매트릭스(14크기×17상태)는 가로 넘침·44px 미달이 모두 0이었고, 실패는 전부 **연속 조작**에서 나왔다. 그래서 검증은 캡처보다 조작 순서를 본다.
- 검증 수준: ego 에뮬레이션 검증, 실기기 미확인. 실기기 iOS Safari·Android 가상 키보드, 한글 IME 조합, 터치 선택 손잡이는 확인하지 않았다.

## 동작 계약(의무)

확인 방법의 API 이름은 웹(ego) 예다. 다른 스택은 같은 상태를 그 스택의 수단으로 기록한다.

| 계약 | 실행 문장 | 확인 방법 |
|---|---|---|
| 초안·선택 보존 | 초안, 선택 범위와 방향은 접기·펼치기·회전·폭 변경·근거 열고 닫기 뒤에도 그대로다. 편집 중(초점이 있거나 초안이 있음)에는 자동으로 접지 않는다. 첫 로드에는 입력창에 자동 초점을 주지 않는다 | 전환마다 전후의 초안과 선택 양끝·방향을 비교한다(웹 예: `value`, `selectionStart/End`, `selectionDirection`). 초점은 조작별 목적지로 본다: 첫 로드 → 입력창이 아님, 근거 닫기 → 연 칩(아래 행), 입력으로 다시 들어오면 → 저장된 선택으로 편집 재개 |
| 읽는 위치 유지 | 사용자가 위로 올려 읽는 중이면 새 이벤트가 와도 스크롤을 옮기지 않는다. 맨 아래에 있을 때만 따라간다 | 답이 흐르는 중 위로 스크롤 → 이벤트 몇 개 수신 → 읽던 요소의 화면 위치가 그대로인지(웹 예: 대화 영역 `scrollTop`, 요소 rect) |
| 근거 도달과 복귀 | 모든 출처·근거는 터치와 키보드로 열린다. 닫으면 초점은 연 칩으로, 스크롤은 읽던 위치로 돌아온다. 입력 중에 열었어도 같고, 초안·선택은 위 행대로 남는다 | 입력에 선택을 둔 채 칩을 터치로 열기 → 내용 끝까지 이동 → 닫기 → 초점이 그 칩, 읽던 위치 같음, 초안·선택 같음. 키보드 Enter/Escape도 따로 |
| 중지·재연결 무결 | 같은 이벤트를 다시 받아도 논리 ID로 한 번만 그린다. 중지 뒤 늦게 온 이벤트는 상태를 되돌리지 않는다. 중지까지 받은 부분 결과는 "중지됨" 표시와 함께 남긴다 | fixture로 같은 ID 이벤트 재전송 → 항목 수와 표시 상태. 중지 → 늦은 이벤트 주입 → "중지됨"이 남는지 |
| 대기·미지원·실패 구분 | 기다리는 중, 이 기기·설정에서 못 함, 시도했지만 실패를 서로 다른 글과 상태로 보인다. 색만으로 구분하지 않는다 | 세 상태를 각각 만들어 글자·접근 가능한 이름이 다른지 |
| 진행은 실제 이벤트만 | 단계 이름은 받은 이벤트에서만 가져온다. 받지 않은 단계를 미리 보여 주지 않는다. 경과 시간은 실제 시작을 확인한 시점부터 클라이언트가 셀지, 서버 값을 쓸지 프로필에 정한다. 완료 시간이나 진행률을 추정해 사실처럼 보이지 않는다 | 미리 만든 상태가 아니라 **실제로 보낸 흐름**에서 단계가 이벤트 순서와 같은지, 경과 시간이 정한 방식대로 늘고 끝·중지에서 멈추는지 |
| 조작 영역과 확대 우선 | 조작 영역 44px과 200% 글자 대응이 높이 상한보다 우선한다. 44px 대상과 허용 예외는 [부품별 동작 계약](system.md#부품별-동작-계약)을 따른다. 높이가 모자라면 글자를 줄이거나 내용을 자르지 않고 배치를 바꾼다 | 200% 글자·폰 가로에서 `measureUI`의 후보·검사 수·누락 범위를 검토한 뒤, 입력·전송·중지·출처 칩을 실측·실조작해 판정한다. 후보 0만으로 합격이라 하지 않는다 |

## 구현에서 자주 깨지는 곳

검증에서 실제로 나온 실패 유형이다. 위 계약을 지키려다 생기는 함정이며 계약을 대신하지 않는다.
- 각 항목 "규칙"의 사용자 결과와 적용·제외 조건은 의무다. "원인(웹)"과 괄호 속 "웹 예"의 구현·측정 수단은 예시이며, 다른 스택은 동등한 수단으로 검증한다.
- 접힌 입력, 근거 패널/시트 전환, 단축키처럼 조건이 붙은 항목은 그 배치를 채택한 경우에만 본다. 채택하지 않았으면 비해당이다.

1. **탭 하나가 두 번 먹힘** (접힌 입력을 채택한 경우)
   - 증상: 접힌 입력을 탭했더니 펼쳐지면서 초점이 새로 나타난 도구 버튼으로 간다.
   - 원인(웹): pointerdown에서 펼쳐 레이아웃이 먼저 바뀌고, 같은 탭의 남은 touchend/click이 새 버튼 위에 떨어진다.
   - 규칙: 탭 한 번은 조작 하나만 일으킨다. 곧이은 별개의 탭은 그대로 동작한다. (웹 예: 펼침은 focus에서만 한다. 그 탭의 남은 click만 한 번 버리고, 새 pointerdown/touchstart/keydown이 오면 즉시 해제한다. 시간 창(예: 0.5초) 필터는 별개 탭을 삼켜서 다시 실패했다.)
   - 확인: 실제 터치로 접힌 입력 탭 → 초점이 입력창. 이어서 바로 도구 버튼 탭 → 그 버튼이 동작.
2. **확대하면 줄이 겹침**
   - 원인(웹): 고정 px line-height.
   - 규칙: 200% 글자에서도 줄이 겹치지 않고, 입력 높이와 최대 줄 수가 글자 크기를 따라간다. (웹 예: line-height는 단위 없이 쓰고, 높이·최대 줄 수는 계산된 line-height와 padding에서 구한다.)
   - 확인: 200% 글자에서 줄마다 위치가 겹치지 않는지.
3. **접힌 미리보기에 이웃 줄 조각이 비침** (접힌 입력을 채택한 경우)
   - 상황: 초안이 있는 접힌 입력을 사용자가 읽으려고 스크롤한 상태.
   - 규칙: 접힌 미리보기에는 프로필에서 정한 줄 수만큼 온전한 줄만 보이고, 이웃 줄 조각이 비치지 않는다. (웹 예: 내부 스크롤을 줄 단위로 스냅하고, padding 띠는 clip-path로 자른다.)
   - 확인: 접힌 상태에서 내부 스크롤 후 캡처를 확대해 위·아래 줄 조각이 없는지.
4. **입력 중 캐럿 줄이 가려짐**
   - 원인(웹): 줄 스냅·자동 높이 뒤 scrollTop이 캐럿을 따라가지 않는다.
   - 규칙: 입력·캐럿 이동·높이 변화 뒤 활성 선택 끝이 있는 줄이 보인다. 사용자가 입력창 안을 직접 민 스크롤은 되돌리지 않는다. (웹 예: scrollTop을 보정한다. 역방향 선택(Shift+↑)에서는 활성 끝이 selectionStart라서 selectionEnd만 보면 틀린다.)
   - 확인: 최대 줄 수를 넘게 입력 → 맨 끝·중간에서 캐럿 이동 → Shift+↑ 선택 → 매번 캐럿 줄이 보이는지. 직접 스크롤한 뒤에는 위치가 유지되는지.
5. **전환 조건이 두 곳** (근거 패널/시트 전환을 채택한 경우)
   - 증상: 근거 패널이 특정 폭 구간에서만 아래로 떨어진다.
   - 원인(웹): 전환을 가독 폭으로 정의했는데, 구현은 고정 폭 미디어 쿼리 안에만 있었다.
   - 규칙: 전환 조건은 한 곳에서만 정한다. (웹 예: 가독 폭 계산 하나에서 정하고 미디어 쿼리에 따로 두지 않는다.)
   - 확인: 정한 경계 폭 ±1px에서 실제 배치를 측정한다. 소스의 미디어·컨테이너 쿼리와 JS 분기도 찾는다.
6. **키보드로 연 메뉴에 못 들어감**
   - 규칙: 키보드로 연 메뉴의 항목에 키보드로 도달하고, Escape로 연 버튼에 돌아온다. 열 때 첫 항목에 초점을 줄지와 Tab 이동은 채택한 부품 계약(system의 메뉴 disclosure·모달)을 따른다. 모달 시트로 구현한 메뉴만 초점을 격리한다. 비모달 disclosure는 Tab으로 다음 조작으로 나갈 수 있다.
   - 확인: Enter로 열기 → 항목 도달 → Tab → Escape 각각 뒤의 초점.
7. **단축키가 특정 초점에서만 동작** (단축키를 채택한 경우)
   - 증상: 입력창으로 가는 `/` 같은 단축키가 body 초점일 때만 된다.
   - 규칙: 단축키는 초점 위치와 상관없이 동작한다. 단 편집 요소에 초점이 있을 때, 초점을 격리한 모달(시트, 모달로 구현한 메뉴)이 열렸을 때, 보조키가 눌렸을 때, 음성 기능을 쓰는 중에는 받지 않는다.
   - 확인: 칩·버튼에 초점을 둔 채 누르기, 입력 중·모달 열림에서 누르기를 각각.
8. **경과 시간이 실제 흐름에서 멈춤**
   - 증상: "진행 중 N초"가 미리 만든 상태에서는 흐르지만 실제로 보낸 흐름에서 0초에 멈춘다.
   - 규칙: [진행 계약](#동작-계약의무)을 실제 전송 흐름에서 확인한다. 미리 만든 상태만으로 판정하지 않는다.
   - 확인: 입력 → 전송 → 몇 초 뒤 값이 늘었는지, 끝·중지에서 멈췄는지.
9. **아이콘 버튼 크기가 화면마다 다름**
   - 원인(웹): 아이콘 버튼 글자 크기가 부모를 상속한다.
   - 규칙: 같은 역할의 아이콘 버튼은 화면이 달라도 크기가 같다. 토큰으로 고정하고 [한 디자이너 점검](system.md#한-디자이너-점검)의 대조에 넣는다. (웹 예: `getComputedStyle`의 글자 크기와 rect로 측정한다. 네이티브는 렌더된 크기 증거로 대신한다.)

## 배치 예시(프로젝트가 고른다)

아래 값은 **한 프로젝트에서 검증한 권장값**이다. 다른 프로젝트는 출발점으로 쓰고, 고른 값을 프로필에 적는다. 그 프로젝트는 [방향 선택](system.md#방향-선택)에서 미니멀(흰 바탕, 강조색 하나)과 문서형 배치(사용자 말만 말풍선, 답은 본문)를 골랐다. 레퍼런스 16곳, 시안 4테마×2배치를 공유 fixture로 비교했다.

표는 배치·높이·줄 수·시간 목표처럼 프로젝트가 고르는 값만 담는다. 조작 영역·확대 우선, 근거 복귀, 이벤트 처리, 진행 표시는 [동작 계약](#동작-계약의무)을 따르며 여기서 고르지 않는다.

| 항목 | 권장값 |
|---|---|
| 모바일 상단 | 얇은 한 줄 바(☰ + 경로) |
| 입력 기본 상태 | 접힌 한 줄 입력. 사용자가 터치하거나 키보드 초점으로 들어올 때만 펼친다. 첫 로드에는 자동 초점 없음 |
| 폰 세로 높이 예산 | 바 + 접힌 입력이 화면 높이 15% 이하(390×844에서 106px, 12.6%) |
| 폰 가로 높이 예산 | 15%는 44px 조작 두 개만으로도 넘으므로 따로 상한 103px(바 실제 45 = CSS 최소 44 + 1px 선, 접힌 입력 58, 기본 글자 크기 조건) |
| 펼친 입력 | 최대 5줄, 넘으면 내부 스크롤 |
| 높이가 모자랄 때 | 순서대로: 바 숨김 → 입력 최대 줄 수 축소(도구 줄 제거) → "키보드 닫고 읽기". 대화 최소 가독 높이 190px |
| 근거 여는 방식 | 본문 최소 가독 폭(한글 약 32자, 560px) + 패널이 함께 들어가면 옆 패널, 아니면 하단 시트(스크림·손잡이) |
| 접수 표시 시간 | 보내면 100ms 안에 사용자 말풍선과 접수 표시(실측 1~2ms) |

프로필에 고정할 항목:
- 배치: 문서형/말풍선형, 답이 본문인지
- 모바일 바와 입력 기본 상태(접힘 여부)의 높이, 폰 세로·가로 높이 상한
- 접힌 입력을 채택했다면 미리보기 줄 수, 펼친 입력의 최대 줄 수, 높이가 모자랄 때의 축소 순서, 대화 최소 가독 높이
- 근거 여는 방식과 전환 조건(계산식과 값)
- 접수 표시 시간 목표, 진행 표시에 쓰는 이벤트 종류, 경과 시간 출처(클라이언트 계산 / 서버 값)
- 단축키 채택 여부, 키와 제외 조건
- 음성 기능 채택 여부·종류, 진입점 자리
- 허용한 예외와 이유([한 디자이너 점검](system.md#한-디자이너-점검))

## 답 구성

- 답은 결론 한 줄로 시작한다. 그 뒤는 질문에 따라 고른다: 글, 표, 그래프, 도형(흐름·비교). 시각 블록은 의무가 아니다. 글로 충분하면 글만 쓴다.
- 블록 상태
  - 대기: 결론과 글은 먼저 보이고, 블록 자리에 "그리는 중"을 표시한다.
  - 미지원: 이 화면이 그 블록 종류를 그릴 수 없으면 그렇다고 적고 같은 내용을 글이나 표로 보인다.
  - 실패: 실패했다고 적는다. 받은 내용이 있으면 남긴다. 빈 자리나 깨진 그림으로 두지 않는다.
- 출처 칩: 블록 전체의 근거는 블록 머리에, 문장의 근거는 문장 끝에 둔다. 여는 방식은 프로필에서 고른 배치를, 도달과 복귀는 동작 계약을 따른다.
- 진행 표시: [진행 계약](#동작-계약의무)을 따른다.
- 합성 예: "두 기준을 비교하면?" → 결론 한 줄 + 비교 표 + 행마다 출처 칩. "이 절차가 어떻게 이어지나?" → 결론 한 줄 + 흐름 도형. "이 용어 뜻은?" → 글만.

## 음성을 나중에 붙일 자리

아직 기능 규칙이 아니다. 지금 정하는 것은 셋뿐이다.

- 채택 여부와 종류. 받아쓰기(말을 글로 받아 입력창에서 고친다)와 실시간 음성 대화(시스템도 말로 답한다)는 다른 기능이다.
- 진입점 위치 후보.
- 그 자리를 높이 예산에 남긴다. 나중에 넣어도 높이 상한과 조작 영역을 깨지 않게 한다.

버튼 수, 상태 이름, 말하는 동안의 화면 구성, 말로 할 범위는 지금 정하지 않는다. 미검증 예: 상태를 듣는 중 / 생각하는 중 / 말하는 중으로 나누고, 결론만 말하고 상세는 화면에 둔다.
확정은 그 기능을 따로 설계·검증할 때 한다. 그때 공통 동작 계약(대기·미지원·실패 구분, 중지)을 적용한다.

## 기기·상황 행

행 정의와 `적용 / 비해당 / 미검증` 규칙의 원본은 [ego 검증의 기기·상황 행](ego-validation.md#기기상황-행)이다. 여기서는 대화형에서 추가로 고를 행만 적는다. 채택하지 않은 배치의 행은 비해당이다.

| 추가 행 | 내용 |
|---|---|
| 키보드 가용 높이 fixture | 높이 축소 단계를 채택한 경우. 채택한 단계의 경계마다 viewport 높이를 줄여 축소가 차례로 일어나는지 본다. 단계 수와 값은 프로필을 따른다(예: 여유 / 바 숨김 / "키보드 닫고 읽기"의 3단계) |
| 근거 전환 경계 폭 ±1px | 근거 패널/시트 전환을 채택한 경우. 정한 전환 폭과 그 ±1px |
| 200% 글자 | 입력 줄 겹침, 최대 줄 수 계산, 조작 영역, 높이 상한보다 확대 우선 |
| 폰 가로 | 가로 높이 상한, 펼친 입력, 대화 최소 가독 높이 |

가용 높이 fixture는 **시험 입력**이다. 가상 키보드를 증명하지 않는다. 실제 키보드·IME·선택 손잡이는 실기기로 확인하기 전까지 `미검증`이다.
새 대화 화면에서는 해당 계약과 연속 조작(예: 탭 → 입력 → 캐럿 이동 → 근거 열고 닫기 → 중지)을 검증한다. 작은 수정은 ego-validation의 영향 행 선택을 따르고, 행 안에서도 변경 영향이 있는 계약·조작만 한다. 무관한 조작은 이유를 적고 생략한다.
