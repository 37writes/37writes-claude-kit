# 정돈 규칙

정보 나열, 어긋난 선 끝, 같은 말 반복, 장식 부품처럼 화면을 조잡하게 만드는 것을 막는 규칙과 점검이다. [공통 원칙](system.md#공통-원칙)과 [한 디자이너 점검](system.md#한-디자이너-점검)을 그대로 적용하고 그 위에 더한다.
간격 단계(4/8/12/16/24/32/48/64px), 글자 크기 출발점, 색 역할, 강조색, 대비의 원본은 [system.md](system.md)다. 이 문서는 값을 다시 정하지 않는다. 프로젝트가 고른 값은 [프로젝트 프로필](system.md#프로젝트-프로필)에 고정한다.

## 언제 읽는가

| 경우 | 읽을 절 |
|---|---|
| 새 화면을 처음 만든다 | 의무, 패턴별 권장값, 정돈 점검 |
| 사용자가 화면 전체를 문제 삼는다("정신없다", "조잡하다", "정돈해 줘") | 의무, 패턴별 권장값, 정돈 점검 |
| 기존 화면의 영역·정보·부품 배치를 바꾼다 | 의무. 바뀐 영역만 확인한다 |
| 사용자에게 UI 선택을 실제로 묻는다(높이, 색 방식, 선택 표시, 배치 등) | 예시 화면으로 고르기 |

- **끼어들지 않는 때**: 프로필이 있는 화면의 작은 수정(메뉴 잘림 하나, 라벨 하나, 상태 색 하나)은 기존 토큰·부품으로 고치고 SKILL.md 5절 검증만 한다. 정돈 점검, 예시 고르기, 비교용 분기를 만들지 않는다.
- 기존 방향·프로필 안에서 답이 정해지는 수정은 사용자에게 묻지 않고 그대로 한다. 묻지 않으면 예시 화면도 만들지 않는다.
- 이 문서는 두 층이다. **의무**는 화면 유형과 상관없이 지킬 결과다. **패턴별 권장값**은 특정 패턴에서 검증한 수치이고 합격 상한이 아니라 진단 신호다.
- 근거: 한 비공개 프로젝트의 3열 작업 화면(목록 · 그래프 · 상세)을 이 규칙으로 정돈했다. 같은 상태·폭에서 ego lite로 잰 전/후: 영역별 글자 시작 x의 고유 값 3 → 1, 세 영역의 머리 줄이 높이 48·아래 선 y=96으로 일치, 태그·알약 154 → 0, 보이는 글자 덩어리 141 → 90, 글자 크기 4 → 3종, 굵기 4 → 2종, 강조색을 쓴 요소 57 → 3곳. 다른 모델의 독립 검토에서 너무 뺀 곳(수치 근거로 가는 길, 폰의 "더 보기", 범위 표시)이 나와 되살렸다. 그래서 빼기에는 과업 확인이 붙는다.

## 의무(결과)

화면 유형(소개·읽기·작업·대화형)과 상관없이 지킨다. 숫자 상한은 여기 없다.

1. **같은 역할끼리 기준선 일치.** 한 영역 안에서는 같은 역할의 요소끼리 면 왼쪽·글자 시작·오른쪽 끝을 각각 같은 x에 맞춘다. 나란한 형제 영역 사이에서는 각 영역의 기준점에 대한 같은 역할의 오프셋과 토큰을 비교하며, 서로 다른 열의 viewport x를 같게 만들지 않는다. 역할이 다른 것(트리 깊이, 표의 수치 열, 인용·목록 들여쓰기, 본문과 목차)은 각자 별도 역할이라 서로 맞추지 않는다. 긴 내용·글자 확대 때문에 높이나 위치가 달라져야 하면 잘라서 맞추지 않고 배치를 바꾼다.
2. **같은 역할은 같은 토큰.** 같은 역할의 글자·간격·모서리·선·색은 한 벌이다([한 디자이너 점검](system.md#한-디자이너-점검)). 간격은 system.md의 단계 값을 쓰고, 단계 밖 값(rem 확대 결과, 광학 보정 등)은 이유를 프로필에 적는다.
3. **정보를 뺄 때 판단 과업 보존.** 남길지 뺄지는 반복 여부가 아니라 **판단·비교·다음 행동에 필요한가**로 정한다. 비교할 때 행마다 필요한 근거, 결과가 전체인지 일부인지 알리는 범위, 불확실성·진행·중지 표시는 정상 상태에서도 남긴다. 뺐으면 [정보 이동 표](#정보-이동-표와-과업-확인)와 과업 확인을 남긴다. 목적지에 닿았다는 것만으로 통과시키지 않는다.
4. **장식선과 기능선 구분.** 줄이는 것은 장식선이다. 입력 경계·포커스·표 구분선·차트 축 같은 기능선과 데이터 표현은 줄이는 대상이 아니다([공통 원칙](system.md#공통-원칙)의 색 역할).
5. **강조색은 역할로 쓴다.** 강조색은 선택 표시와 주요 행동 두 역할에 쓴다. 요소 수 제한이 아니다. 링크·포커스·오류/성공 상태색·데이터 범례색은 system.md대로 지키고 강조색을 줄이려고 지우지 않는다. 범례색 위에 강조색으로 선택을 표시하면 명도 대비를 재고([대비 확인](../SKILL.md#4-적용)), 약하면 색이 아닌 표시(크기·굵기·나머지 흐리게 등)를 더한다. 근거 사례에서 유형 색 노드 위 강조색 선택 표시는 1.01~1.24배였다.
6. **내부 표시는 사용자 정보가 아니다.** 내부 ID·내부 용어·개발 메모 알약은 뺀다. 생성 결과의 불확실성은 사용자 정보이므로 개발 메모와 구분해 남긴다.
7. **아이콘 세트 하나.** 제품이 이미 쓰는 세트, 없으면 공개 세트 하나를 쓰고 버전·라이선스를 프로필에 적는다. 그때그때 즉흥으로 그린 아이콘을 섞지 않는다. 세트에 없는 도메인 아이콘은 같은 획 굵기·격자로 만들고 검토받는다.
8. **보이는 높이와 누르는 영역을 나눈다.** 정밀 포인터에서만 낮게 보일 수 있고, 누르는 영역은 [부품별 동작 계약](system.md#부품별-동작-계약)의 44px을 지킨다.
9. **UI 선택은 예시 화면으로 묻는다.** 사용자에게 실제로 물을 때만이다([고르기](#예시-화면으로-고르기)).

## 패턴별 권장값(3열 작업 화면 예)

목록 · 본문(그래프·표 등) · 상세처럼 이웃한 영역 셋이 나란한 작업 화면에서 검증한 값이다. 다른 패턴은 출발점으로만 쓰고, 고른 값은 프로필에 적는다. 소개·읽기·대화형은 [화면 유형](system.md#화면-유형)과 [대화형 패턴](conversational.md)을 따르고, 이 수치로 소개 제목·읽기 본문의 위계를 줄이지 않는다.
권장값을 넘었다고 실패가 아니다. 넘은 곳을 보고 이유가 있으면 프로필에 예외로 적는다.

### 정렬

| 항목 | 권장값 |
|---|---|
| 세로 기준선 | 영역마다 둘: 면의 왼쪽(검색 상자·선택 면·버튼 면)과 글자 시작(제목·탭 첫 글자·행 이름·본문). 세 영역은 영역 기준점 대비 오프셋이 같다 |
| 오른쪽 끝 | 영역 안에서 닫기·수·행 끝 화살표·도구를 한 x에 |
| 머리 줄 | 이웃한 영역이 같은 y·같은 높이, 그 아래 선 하나가 끝까지 이어짐 |
| 버튼 안쪽 여백 | (글자 시작 − 면 왼쪽)과 같게 해서 버튼 글자가 글자 기준선에 떨어지게 |
| 아이콘 열 | 두려면 모든 행에 둔다. 일부 행에만 두지 않는다 |

### 선과 상자

| 항목 | 권장값 |
|---|---|
| 장식선 | 열 경계와 머리 줄 아래, 두 종류. 기능선은 세지 않는다 |
| 구역 나누기 | 선이 아니라 여백과 구역 제목 |
| 카드 | 실제 묶음에만. 영역 안 0~1개가 기본이고, 실제 독립 묶음 수를 카드 수 기준이 바꾸지 않는다 |

### 정보 예산

| 항목 | 권장값 |
|---|---|
| 영역의 질문 | 영역마다 하나를 적는다(예: 주문 목록 "어느 주문을 볼까", 주문 상세 "무슨 상태이고 근거는 무엇인가") |
| 같은 정보 | 화면에 한 번. 역할이 다른 두 곳에 남기면 이유를 적는다 |
| 같은 수 | 여러 번 나오면 하나로 모은다 |
| 상태 태그 | 정상 상태를 알리기만 하는 태그는 붙이지 않는다. 범위·진행·불확실성은 의무 3대로 남긴다 |

### 위계와 부품

| 항목 | 권장값 |
|---|---|
| 글자 | 한 영역에서 크기 3종·굵기 2종. 넘으면 진단 신호 |
| 강조색 | 선택 표시와 주요 행동. 근거 사례는 화면 전체 3곳 |
| 버튼 | solid는 맥락당 한 번, 그 밖은 soft·ghost |
| 모서리 | 토큰 두 개: 조작(`--kit-radius-control`)과 면(`--kit-radius-panel`) |
| 그래프·도표 | 라벨이 선과 겹치지 않음, 무리 제목이 자기 무리 옆, 선택 표시는 이중 링·그림자 없이 보임 |

## 정돈 점검

[언제 읽는가](#언제-읽는가)의 새 화면·화면 전체 문제일 때 SKILL.md 2절(전)과 5절(후)에서 쓴다. ego 사용 규칙은 [ego 검증 절차](ego-validation.md)를 따른다. 측정 결과만으로 합격이라고 하지 않는다.

### 1. 역할과 선택자를 먼저 정한다

측정 전에 영역과 역할을 선택자로 적는다. 어느 요소가 면 왼쪽인지, 글자 시작인지, 오른쪽 끝인지, 머리 줄인지, 태그·알약인지 정한다. 측정 뒤에 불편한 요소를 선택자에서 빼서 숫자를 맞추지 않는다. 뺀 요소는 이유와 함께 "제외"에 적는다.

- 선택자가 0개를 찾으면 성공이 아니라 **미검증**이다.
- SVG·canvas 안의 그림, 가상 목록에서 아직 DOM에 없는 행, iframe·shadow DOM은 "미검사"에 적는다. 가상 목록은 끝까지 스크롤한 뒤 다시 잰다.
- x를 오름차순으로 정렬한 뒤 군집을 만든다. 각 군집의 최솟값과 0.5px 이내인 값만 같은 군집에 넣고, 그보다 큰 값에서 새 군집을 시작한다. 군집 대표값은 최솟값으로 하며 DOM 순서가 달라도 같은 좌표 집합은 같은 결과를 내야 한다.

### 2. 상태·폭마다 잰다

전용 측정 스크립트는 없다. ego Page에서 `page.evaluate`로 DOM을 읽기만 하는 코드를 쓰고, 다시 돌릴 수 있게 그 코드를 기록과 함께 남긴다. 설정·측정·초기화는 ego 검증 절차대로 같은 실행 안에서 한다.

| 지표 | 읽는 값 |
|---|---|
| 영역별 기준선 | 영역 안에서 역할마다 면 왼쪽(요소 rect.left)·글자 시작(첫 글자 Range의 left)·오른쪽 끝(rect.right) x의 고유 값 개수. 영역 사이는 영역 기준점 대비 오프셋으로 비교 |
| 머리 줄 | 영역마다 머리 줄의 top·높이·아래 선 y |
| 간격 | 역할 요소의 계산된 padding·gap·margin이 system.md 단계 값인지. 단계 밖 값과 이유 |
| 정보량 | 태그·알약 수, 보이는 글자 덩어리 수, 같은 문자열의 반복 |
| 위계 | 영역별 글자 크기·굵기 종류 |
| 강조색 | 강조색을 쓴 요소 수와 위치(글자색·배경·선 중 무엇인지) |

기준선을 읽는 예(선택자는 프로젝트 값으로 바꾼다). `text-left`는 선택 요소의 자손 중 실제로 렌더되고 부모가 `visibility: visible`인 비공백 텍스트 노드를 찾아 첫 글자 Range의 좌표를 읽는다. 글자 좌표를 얻지 못하면 요소 박스로 대체하지 않고 `미검사: 글자 좌표 없음`으로 기록하며, 그 요소는 기준선 고유 값과 검사 수에서 제외한다.

```js
// roles: 측정 전에 정한 역할 → { 선택자, 읽을 끝 }. 0개 매칭은 미검증으로 보고한다.
const roles = {
  "목록 글자 시작": { sel: ".order-list .row-title", edge: "text-left" },
  "목록 오른쪽 끝": { sel: ".order-list .row-end", edge: "right" },
};
const report = await page.evaluate((roles) => {
  const visible = (el) => {
    const r = el.getBoundingClientRect(), cs = getComputedStyle(el);
    return r.width > 0 && r.height > 0 && cs.visibility !== "hidden";
  };
  // 첫 글자: 렌더되고 보이는 비공백 텍스트 노드의 첫 글자 Range. 못 얻으면 null(미검사).
  const textLeft = (el) => {
    const walker = document.createTreeWalker(el, NodeFilter.SHOW_TEXT);
    for (let node = walker.nextNode(); node; node = walker.nextNode()) {
      const i = node.data.search(/\S/);
      if (i < 0 || getComputedStyle(node.parentElement).visibility !== "visible") continue;
      const range = document.createRange();
      range.setStart(node, i);
      range.setEnd(node, i + (node.data.codePointAt(i) > 0xffff ? 2 : 1));
      const r = range.getBoundingClientRect();
      if (r.width > 0 && r.height > 0) return r.left;
    }
    return null;
  };
  const edgeX = (el, edge) => edge === "text-left" ? textLeft(el)
    : edge === "right" ? el.getBoundingClientRect().right : el.getBoundingClientRect().left;
  // 오름차순 정렬 뒤 군집. 군집 최솟값과 0.5px 이내면 같은 군집, 대표값은 최솟값.
  const cluster = (xs) => {
    const reps = [];
    for (const x of [...xs].sort((a, b) => a - b))
      if (!reps.length || x - reps[reps.length - 1] > 0.5) reps.push(x);
    return reps;
  };
  return Object.fromEntries(Object.entries(roles).map(([role, { sel, edge }]) => {
    const all = [...document.querySelectorAll(sel)], shown = all.filter(visible);
    const xs = shown.map((el) => edgeX(el, edge)), measured = xs.filter((x) => x !== null);
    return [role, { sel, matched: all.length, inspected: measured.length,
      hidden: all.length - shown.length,
      uninspected: { "글자 좌표 없음": xs.length - measured.length },
      uniqueX: cluster(measured), verdict: measured.length ? "측정" : "미검증" }];
  }));
}, roles);
```

### 3. 같은 방법으로 전과 후를 표로 남긴다

상태·폭마다 표 하나. 전과 후는 같은 route·상태·폭·데이터·선택자로 잰다.

| 역할 | 선택자 | 지표 | 검사 수 | 제외(이유) | 미검사 | 전 | 후 |
|---|---|---|---|---|---|---|---|
| 예: 목록 글자 시작 | `.order-list .row-title` | 고유 x 개수 | 24 | 0 | 가상 목록 25행 이후 | 3 | 1 |

### 정보 이동 표와 과업 확인

정보를 뺐거나 옮겼으면 둘 다 남긴다.

### 4. 사람 눈과 독립 검토

- 사람 눈: 3초 첫인상에서 시선이 선택한 대상에 먼저 가는지, 한 영역에서 시선을 끄는 것이 둘 이상인지 본다.
- 독립 검토: 정돈 점검을 쓴 작업에서만 한다. T1 독립 검증(harness)과 겹치면 하나로 합친다. 작성자와 다른 모델에게 원래 요구, 화면 경로, 레퍼런스, 프로필(확정 토큰·허용 예외)을 주고 작성자의 합격 결론은 주지 않는다.
- 검토자 보고 순서: 첫인상 → 정렬 실측 → 정보(남은 중복 / 너무 빼서 막힌 과업) → 부품 → 고칠 것 최대 10개(문제 → 근거 좌표 → 정확한 값). 새 장식을 더하는 수정에는 무엇을 대체하는지 쓴다.

## 예시 화면으로 고르기

사용자에게 UI 선택을 실제로 물을 때 쓴다. 글로만 묻지 않는다. [방향 선택](system.md#방향-선택)의 시안을 사용자에게 보일 때도 이 절차를 쓴다. 기존 방향·프로필 안에서 해결되는 수정은 묻지 않는다.

1. 선택지마다 같은 상태·폭·데이터를 만든다. 수단은 자유다(쿼리 값, 별도 비교 fixture 등). 제품 화면에 선택지를 바꾸는 스위치 UI는 두지 않는다.
2. ego로 캡처해 선택지 라벨을 붙이고 나란히 붙인 비교 이미지 한 장을 만든다. 작은 차이는 같은 부위를 확대해 잘라 붙인다. 색이 쟁점이면 흑백판을 하나 더 둔다.
3. 작성자가 이미지를 직접 열어 확인한 뒤 사용자 화면에 연다(macOS `open` 같은 로컬 뷰어, 또는 ego Page).
4. 이미지 경로와 차이 설명(무엇이 같고 무엇만 다른지)을 함께 묻는다. 추천이 있으면 이유를 붙인다.
5. 고른 결과와 버린 안의 이유를 프로필에 고정한다. **채택하지 않은 코드 분기는 지우고** 비교 이미지만 남긴다. 계속 쓸 비교 fixture가 있으면 위치를 프로필에 적는다.

개인정보는 [방향 선택](system.md#방향-선택)의 규칙을 따른다. 사용자 정보가 보이는 화면은 캡처하지 않는다.
