# design: 나의 AI 디자이너

목표는 **같은 사람이 만든 제품처럼 일관된 UI**다. 명확한 위계·정렬·절제된 표현을 유지하면서 색과 글꼴로 개성을 만든다. Apple은 이런 원칙의 참고이며, 모든 화면을 홍보 홈페이지처럼 만들라는 뜻은 아니다.
질문·보고는 한국어. 등급·계획·독립 검증·기록·배포는 `../harness/SKILL.md`를 따른다.

## 1. 디자인 계약부터 읽기

먼저 [공통 규칙과 프로필](references/system.md)을 읽는다.
- 프로젝트의 디자인 시스템/부품 라이브러리, `docs/design-system.md`(또는 기존 대응 문서), CLAUDE.md·AGENTS.md, 실제 CSS와 글꼴 로딩을 확인한다.
- 프로필이 있으면 테마·토큰·부품·화면 유형을 **재사용**한다. 새 작업마다 방향 3개를 다시 묻거나 임의의 값을 만들지 않는다.
- 프로필이 없으면 기존 색·글꼴·부품을 추출한다. 사용자 방향이 주어졌으면 그 안에서 진행한다. 새로운 시각 방향 선택이 필요할 때만 미리보기 2~3개(배치와 색·글꼴)를 보여 준다.
- 선택은 프로필에 고정한다. 승인된 값과 임시 추천값을 구분하고, 미확정 값을 “사용자 브랜드”라고 부르지 않는다.
- **테마**(외관)와 **시스템 버전**(규칙/부품 변경)을 구분한다. kit가 업데이트되어도 기존 프로젝트를 자동 이관하지 않는다.

## 2. 현재 화면과 문제 확인

브라우저 작업은 **ego lite만** 쓴다. [ego 검증 절차](references/ego-validation.md)를 읽고 설치된 `ego-browser skill` 안내를 따른다.
`shot.py`, 직접 headless Chrome, 별도 Playwright 브라우저를 우회 경로로 쓰지 않는다. ego가 안 되면 원인과 미검증 범위를 보고한다.

- 로컬/배포 화면에서 홈·상세·작업 화면 등 바뀌는 유형을 확인하고 모바일/데스크톱 전 캡처를 남긴다.
- 기존 메뉴·탭·검색·키보드 포커스·모드 전환을 먼저 조작한다. 로그인 필요 화면은 실제 로그인 상태와 로컬 모의 상태를 구분한다.
- 테마 프레임워크의 변수·커스텀 CSS·head 삽입 위치를 찾는다. 증상과 코드 흐름을 연결하고 영향 큰 문제 3개부터 설명한다.
- 새 화면은 비교할 전 화면이 없음을 적고 승인된 기준 화면/프로필과 비교한다.

## 3. 동일 규칙으로 구성

- **공통**: 위계, 간격 단계, 버튼·입력·탭 상태, 모바일 동작, 접근성.
- **테마**: 의미별 색, 글꼴, 모서리, 그림자, 허용된 재질. 고정값은 [CSS 자산](assets/core.css)과 [테마](assets/themes/neutral.css)에서 가져오거나 기존 시스템에 매핑한다.
- **화면 유형**: 소개는 핵심 가치/실물 예시, 읽기는 본문 가독성, 작업은 탐색/정보 밀도/상태를 우선한다. 서로 다른 유형도 버튼·메뉴 등의 동작 계약은 같다.
- CSS 교체로 DOM 구조·상태 관리까지 바뀐다고 가정하지 않는다. 모바일 메뉴 접기, 탭 이동, 포커스 복귀는 컴포넌트가 구현한다.
- 작은 메뉴 수정이면 관련 토큰/부품만 사용한다. 전체 사이트를 프리셋으로 갈아엎지 않는다.

다음은 **맥락을 보는 진단**이다. 특정 색·서체·모양만으로 AI 디자인이라고 판정하지 않는다.

| 확인할 것 | 개선 기준 |
|---|---|
| 습관적인 그라디언트·네온·glass·그림자 | 프로필에 근거가 있고 정보 구분에 도움이 되는가 |
| 모든 요소를 카드로 감싸기 | 실제 그룹만 묶고 나머지는 정렬·여백·위계로 구분 |
| 템플릿 히어로·아이콘 3열의 반복 | 실제 콘텐츠와 사용자의 첫 작업을 우선 |
| 아이콘·이모지·애니메이션 과다 | 의미가 빠르게 전달되거나 상태 변화에 필요한 것만 |
| 서체·색·간격이 페이지마다 달라짐 | 정해진 토큰과 부품 사용. 서체 하나도 충분한 위계를 만들면 허용 |
| 흐린 글자, 입력 경계·포커스가 안 보임 | 실제 배경에서 대비 확인. 장식선과 기능선 분리 |
| 중복 위젯, 가짜 수치·후기, 빈 홍보 문구 | 실제 내용만 남기고 불필요한 요소 제거 |
| 제목·탭을 잘라 높이 맞추기 | 핵심 제목은 읽을 수 있게. 긴 메뉴는 축소 대신 정해진 스크롤/접기 |
| 한글이 한 글자씩 꺾이거나 버튼이 찌그러짐 | 본문 keep-all + 긴 문자열 탈출, 메뉴 nowrap + shrink 방지 + 부모의 폭/넘침 설계 |

## 4. 적용

- 자산 원본을 프로젝트에 그대로 복사하고 버전·해시·경로를 프로필에 적는다. 기존 변수와 연결하는 매핑 파일을 별도로 둔다. kit 로컬 절대경로를 제품 빌드에 참조하지 않는다.
- 기존 프레임워크는 테마 변수 → 커스텀 CSS → 폰트 로딩 순으로 적용한다. 마크업 재정의는 동작/접근성 때문에 필요할 때만 한다.
- 덮어쓰기가 안 되면 빌드된 CSS의 특이성·순서·모드 속성·가상 클래스·가상 요소를 조사한다. Chirpy의 `:root[data-bs-theme]`와 속성 없는 시스템 모드도 확인한다.
- 테두리는 `border-bottom: 1px solid ...`처럼 style까지 지정한다. `border: 0`을 색만으로 복원하지 않는다.
- 실제 바탕별 글자 대비를 `sh <base directory>/../../scripts/py.sh <base directory>/../../scripts/contrast.py ...`로 확인한다. 본문 4.5:1, 큰 글자·기능선·아이콘 3:1을 구분한다. 이 도구는 3:1 쌍에도 exit 1이므로 출력 수치로 판정한다.
- 코드 주석·줄 번호, placeholder, 선택/오류/포커스 상태도 포함한다. 강조색 하나 규칙은 오류·성공 상태색과 데이터 시각화 범례를 지우라는 뜻이 아니다.
- 검색·목차·다크 모드·접근성 기능을 보존한다. 방향 때문에 기능을 빼야 할 때만 사용자에게 이유와 대안을 제시한다.

## 5. 검증과 완료

[ego 검증 절차](references/ego-validation.md)의 매트릭스와 실조작을 수행한다. 캡처 한 장이나 도우미의 후보 0개는 합격이 아니다.

1. 같은 화면·폭·테마·상태의 전후를 비교한다. 신규 화면은 기준 화면과 비교한다.
2. 실제 viewport/터치 설정을 확인하고 메뉴 열기·선택·닫기, 탭의 첫/마지막 항목, 키보드 이동을 검사한다.
3. 긴 한글, 글꼴 로드/대체, 글자 확대, 코드·표, 빈/오류/로딩 등 이번 변경에 해당하는 경계를 검사한다.
4. 프로젝트 빌드·린트·기존 테스트, 변경 범위, 토큰 원본과 매핑을 확인한다. T1 이상은 harness의 독립 검증.
5. 검증자에게 프로필, 실행/캡처 경로와 원래 사용자 요구를 주고 독립적으로 실패 시나리오를 선택하게 한다. 작성자의 합격 결론을 답으로 주지 않는다.

보고: 적용한 시스템/테마 버전, 바뀐 화면, 검증한 폭·상태·조작, 전후 캡처, 남은 실패/미검증. 에뮬레이션을 실기기 검증으로, 로컬 성공을 배포 성공으로 보고하지 않는다.
