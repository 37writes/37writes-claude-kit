# commit: 규칙에 맞는 커밋

## 형식

```
type(scope): 한국어 요약

- 무엇을 바꿨는지 / 왜 바꿨는지
- (필요할 때만) 추가 설명

Refs: docs/plans/2026-10-14-social-login.md
```

- **type** (영어, 필수)

  | type | 쓰는 경우 |
  |---|---|
  | feat | 새 기능 |
  | fix | 버그 수정 |
  | docs | 문서만 변경 (README, devlog, 주석) |
  | refactor | 동작은 같고 구조만 개선 |
  | perf | 성능 개선 |
  | test | 테스트 추가·수정 |
  | style | 포맷, 공백 등 의미 없는 변경 |
  | build | 빌드 설정, 의존성 |
  | ci | CI/CD 설정 (amplify.yml, workflows) |
  | chore | 그 외 잡일 |
  | revert | 이전 커밋 되돌림 |

- **scope** (영어 소문자, 선택): 바뀐 모듈이나 영역. 예) `auth`, `api`, `ui`, `nav2`, `build`. 한 프로젝트 안에서 같은 영역은 같은 scope를 쓴다 (`git log --format=%s | head -50`으로 기존 scope 확인).
- **요약** (한국어, 필수): 50자 이내, 마침표 없이, "~추가 / ~수정 / ~분리 / ~제거"처럼 명사형으로 끝낸다.
- **본문** (선택): 요약만으로 이유가 드러나지 않을 때 `- ` 목록으로. "왜"를 우선 적는다.
- **Refs** (선택): 관련 기획서가 `docs/plans/`에 있으면 경로를 적는다.
- 하위 호환이 깨지면 type 뒤에 `!`를 붙이고 본문 끝에 `BREAKING CHANGE: 설명`.

레포의 commit-msg 훅이 첫 줄 형식을 검사한다. 거부되면 메시지를 고쳐서 다시 커밋한다 (`--no-verify`로 우회하지 않는다).

## 절차

1. `git status`, `git diff`, `git diff --staged`로 변경 내용을 파악한다.
2. **논리 단위로 나눈다.** 서로 다른 목적의 변경(예: 버그 수정 + 무관한 리팩터링)이 섞여 있으면 커밋을 나누자고 제안한다. 사용자가 이미 스테이징해 둔 것이 있으면 그 범위를 존중한다.
3. 파일은 경로를 지정해서 스테이징한다. `git add -A` / `git add .`는 쓰지 않는다.
4. 다음 파일은 스테이징하지 않고 사용자에게 알린다: `.env*`, 키·인증서(`*.pem`, `*.key`, `*.p12`), `credentials`, 대용량 바이너리, 빌드 산출물.
5. 커밋한다. 여러 줄 메시지는 heredoc으로 전달한다.
6. **push는 하지 않는다.** 사용자가 요청할 때만 하며, 그때도 대상 브랜치와 배포 영향(예: Amplify 자동 배포)을 알리고 확인을 받는다.
7. 결과를 짧게 보고한다: 커밋 해시와 첫 줄 목록.

의미 있는 작업 단위가 끝났다면 마지막에 "/kit:devlog 로 기록할까요?"라고 한 줄 제안한다.
