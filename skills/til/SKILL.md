# til: 배운 것 빠르게 저장

개발 흐름을 끊지 않는 것이 최우선이다. **질문 없이, 짧게, 바로 저장**하고 하던 작업으로 돌아간다.
나중에 `/kit:blog`가 이 메모를 블로그 글의 원료로 쓴다.

## 무엇을 저장하나

- 인자가 있으면 (`/kit:til QoS 개념`) 그 주제만.
- 없으면 **방금까지의 대화**에서 새로 알게 된 개념, 해결한 문제의 원리를 하나 고른다. 후보가 여러 개로 뚜렷하게 갈리면 그때만 AskUserQuestion으로 고르게 한다 (여러 개 선택 가능 → 메모 여러 개).
- 단순 작업 기록(무엇을 했다)은 devlog의 몫이다. TIL은 **다른 사람에게 설명할 수 있는 개념이나 원리**여야 한다.

## 저장 위치

메모 저장소: `~/Documents/dev/my-notes` (비공개 git 저장소)
- 없으면 한 번만 확인을 받고 만든다: `git init -b main`, `til/` 폴더, README 한 줄. 원격(비공개 GitHub)은 사용자가 원할 때 `gh repo create my-notes --private --source . --remote origin`.
- 파일: `til/YYYY-MM-DD-<영어-slug>.md` (같은 이름이 있으면 `-2`)

## 메모 형식

````markdown
---
title: ROS2 QoS — Reliable과 Best Effort의 차이
date: 2026-10-14
project: sola-api       # 메모를 만든 레포 이름 (레포 밖이면 생략)
category: 회사           # 그 레포 CLAUDE.md 프로필의 구분 (회사/대학원/개인), 없으면 생략
tags: [ros2, dds, qos]
status: draft           # draft → posted
---

## 한 줄 요약
...

## 어떤 상황이었나
실제로 겪은 문제나 맥락. 이 부분이 글을 살아 있게 만든다.

## 개념
원리를 설명. 처음 보는 사람이 이해할 수 있게.

## 예시
```코드
최소한의 동작하는 예시
```

## 주의할 점
흔한 실수, 헷갈리는 부분 (없으면 생략)

- 공식 문서 링크 등 (대화에서 나온 것만, 지어내지 않는다)
````

규칙:
- 내용은 한국어, 용어·코드는 원문. 정확하지 않은 내용은 쓰지 않는다. 확신이 없는 부분은 "(확인 필요)"라고 표시한다.
- 회사 맥락은 그대로 적어도 된다 (비공개 저장소이고, 공개 전에 /kit:blog가 걸러낸다). 단 **비밀번호, 키, 토큰, 고객 개인정보는 절대 적지 않는다.**
- project와 category를 꼭 채운다. /kit:blog가 회사 정보를 거를 때 이 값을 기준으로 한다.

## 저장 후

1. 메모 저장소에서 커밋: `docs(til): <title>` (경로 지정해서 그 파일만)
2. 사용자에게는 **두 줄 이내로** 보고하고 끝낸다:
   `📝 til/2026-10-14-ros2-qos.md 저장 — ROS2 QoS (Reliable vs Best Effort)`
3. 현재 레포가 kit 프로젝트면, 다음 devlog의 **TIL** 섹션에 이 메모 경로를 넣는다.
