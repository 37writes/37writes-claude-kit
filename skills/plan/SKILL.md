# plan: 질문으로 만드는 기획서

사용자는 기획을 길게 설명하는 것을 싫어한다. **Claude가 코드와 기록을 먼저 읽고, 추천 답이 달린 질문을 던져서 사용자는 고르기만 하게** 만든다.

사용자에게 하는 질문과 보고는 모두 **한국어**로 한다.

인자로 한 줄 설명이 오면 (`/kit:plan 소셜 로그인 추가`) 거기서 시작하고, 없으면 무엇을 만들지 한 줄만 묻는다. harness가 이 파일을 경로로 읽었으면 harness가 파악한 요청이 인자다 (다시 묻지 않는다).
등급·승인·기록의 정의는 harness 공통 규칙(`<base directory>/../harness/SKILL.md`)을 따른다. 이 스킬은 기획서 형식과 질문 방법만 정한다.

"구조 잡아줘", "개발 순서 정해줘"처럼 프로젝트 전체를 묻는 요청이면 아래 "프로젝트 설계"를, 기능 하나면 1~6단계를 한다.

## 프로젝트 설계 (`docs/plans/project.md`)

프로젝트 전체의 구조와 개발 순서를 하나의 파일로 둔다. 1단계처럼 먼저 조사하고, 2단계처럼 추천값을 단 질문으로 갈림길(모듈 경계, 순서)만 고르게 한다.

```markdown
---
title: <프로젝트 이름> 설계
type: project
date: 2026-10-14
---

# <프로젝트 이름> 설계

## 목표
누가, 왜 쓰는가. 첫 버전에서 되어야 하는 것.

## 구조
- 모듈 경계: `src/api/` — 무엇을 맡고 무엇을 맡지 않는가
- 데이터 흐름, 외부 시스템

## 기능 목록과 개발 순서
1. 로그인 — [기획서](2026-10-14-social-login.md) · in-progress
2. 보고서 생성 — 기획 전
3. 초기 설정 — 완료 a1b2c3d

## 공통 결정
- A 대신 B → 이유
```

- 기능 하나를 기획할 때 그 기획서를 해당 항목에 링크하고 상태를 갱신한다.
- 이 파일은 지우지 않는다. 항목의 작업이 끝나 기획서가 지워지면 링크를 `완료 <커밋>`(그 작업의 마지막 커밋)으로 바꾼다.
- 승인과 커밋은 6단계와 같다: `docs(plan): <프로젝트> 설계`.

## 1. 먼저 조사 (질문 전에)

- `CLAUDE.md`(프로필: 구분, 스택, 배포 방식)·`AGENTS.md`·`README`
- `docs/plans/project.md`(있으면): 이 기능이 들어갈 항목과 공통 결정
- `docs/plans/`의 진행 중 기획서: 겹치거나 이어지는 작업, `## 남은 일`
- 관련 코드: 이 기능이 닿을 모듈, 비슷한 기존 구현, 데이터 구조
- 끝난 작업은 기획서가 지워졌으니 필요하면 git 기록에서 찾는다 (harness 공통 규칙 "지운 기획서 찾기")

조사 결과로 답할 수 있는 건 묻지 않는다. 질문의 추천값도 조사 결과에서 만든다.

## 2. 질문 (최대 2라운드)

AskUserQuestion으로 한 라운드에 최대 4개씩. 각 질문에는 조사 기반의 **추천 옵션을 첫 번째에 "(추천)"으로** 둔다.
기능 크기에 맞게 필요한 것만 고른다. 작은 기능이면 1라운드로 끝낸다.

| 주제 | 묻는 것 |
|---|---|
| 목적 | 누가, 왜 쓰는가. 이게 없으면 지금 무엇이 불편한가 |
| 범위 | 이번에 포함할 것 / 일부러 뺄 것 (가장 좁은 첫 버전) |
| 동작 | 핵심 흐름, 실패했을 때 어떻게 되어야 하는가 |
| 기술 선택 | 갈림길이 있을 때만 (라이브러리, 저장 방식, 구조). 각 옵션의 장단점을 description에 |
| 완료 기준 | 무엇이 되면 "끝"인가 (테스트, 화면, 배포) |

사용자가 Other로 길게 답하면 그 내용을 우선한다.

## 3. 설계 점검

질문이 끝나면 스스로 점검한다 (사용자에게 묻지 않음):
- 변경할 파일/모듈과 새로 만들 것
- 엣지 케이스와 실패 상황 (빈 값, 네트워크 오류, 권한, 동시 실행, 대용량)
- 기존 기능에 미치는 영향, 하위 호환
- 테스트 방법 (프로필의 테스트 명령 기준; 없으면 수동 확인 절차)
- 배포 영향 (Amplify 자동 배포라면 main 반영 = 배포, 프로필 자동 배포 정책이 있으면 정책 안/밖)

## 4. 기획서 작성

파일: `docs/plans/YYYY-MM-DD-<영어-slug>.md` (예: `2026-10-14-social-login.md`)

```markdown
---
title: 소셜 로그인 추가
date: 2026-10-14
status: draft          # draft → approved → in-progress → done | abandoned (그만두면 이유를 남은 일에)
tier: T1               # harness 공통 규칙의 등급
---

# 소셜 로그인 추가

## 목표
한두 문장. 누가, 왜.

## 범위
- **포함**: ...
- **제외**: ... (이유)

## 동작
핵심 흐름을 단계로. 실패 시 동작 포함.

## 설계
- 변경: `path/file` — 무엇을
- 신규: `path/file` — 무엇을
- 데이터/API 변경이 있으면 간단히

## 결정 & 이유
- A 대신 B → 이유 (질문에서 고른 선택은 모두 여기에)

## 엣지 케이스 & 리스크
- ...

## 기획 반박 (반박 대상만)
- 검토자: agent·model·Task/Dispatch ID, 보고서 경로
- 반례 1 ... → 수용|기각, 이유 (계획에서 고친 곳)

## 작업 단계
- [ ] S1. ... — 담당 — 완료 조건 (커밋 하나 크기로 쪼갠다)
- [ ] S2. ... — Coder — `npm test` 통과
- [ ] S3. 독립 검증 — Validator — S1·S2 검사 재실행, 변경 범위 확인, 완료 기준에서 직접 고른 실패 시나리오 1~3개

## 완료 기준
- 사용자가 보게 될 결과로 쓴다 (예: 배포 사이트에서 로그인 성공)

## 승인 필요 (T2만)
- 바꾸는 것, 미리보기 명령(`cdk diff`, `terraform plan` 등), 롤백 방법

## 열린 질문
- 아직 정하지 않은 것 (없으면 섹션 생략)

## 남은 일
- 다음 세션이 이어받을 것, 사용자만 할 수 있는 확인 (작업 중 채운다. `abandoned`면 그만둔 이유)
```

담당은 /kit:harness의 역할(Coder, Validator, Reporter) 또는 "나"(사용자만 할 수 있는 확인). 혼자 하는 작은 기능이면 담당은 생략해도 된다.
등급(`tier`)은 harness 공통 규칙의 표로 정한다. 커밋 목록은 적지 않는다 (커밋 본문의 `Refs`로 찾는다).

규칙: 내용은 한국어, 코드·파일명은 원문. 작은 기능이면 섹션을 줄여 한 화면 안에 들어오게 쓴다. 빈 섹션은 생략한다.

## 5. 기획 반박

harness 2단계의 "기획 반박" 대상(불확실성이 높거나 영향이 큰 기획)이면 기획서를 다른 모델에게 반박받고, 수용/기각을 "기획 반박" 섹션에 적고 계획을 고친다. 기준·검토자·차단은 harness를 따른다. 사용자에게 묻거나 승인받는 것은 이 뒤에 한다. 대상이 아니면 건너뛴다.

## 6. 확인과 커밋

1. 기획서 핵심(목표, 범위, 작업 단계)을 짧게 보여주고 계획 승인을 받는다 (harness 공통 규칙 "승인"). 수정 요청은 반영한다.
2. 승인되면 `status: approved`로 바꾸고 기획서만 커밋한다: `docs(plan): <기능> 기획`
3. 기획만 요청했으면 여기서 멈춘다. 처음 요청이나 승인에 구현이 들어 있으면 다시 묻지 않고 시작한다. 구현은 harness 절차(작업 지시, 독립 검증, T2 미리보기)를 따른다. 구현을 시작하면:
   - `status: in-progress`로 바꾸고, 작업 단계 체크박스를 진행하면서 체크하고 결과를 한 줄씩 적는다 (기획서 갱신은 그 단계 커밋에 같이)
   - 이 기획에 해당하는 커밋은 본문에 `Refs: docs/plans/<파일>`을 적는다
   - 전부 끝나 `done`이 되거나 그만둬 `abandoned`가 되면 그 작업의 마지막 커밋에서 이 기획서와 보고서 폴더가 지워진다 (harness 공통 규칙 "기록"). 내용은 git 기록에 남는다.

프로필이 없는 레포도 `docs/plans/`만 만들어 진행한다. 작업에 필요한 사실(빌드·테스트·배포)이 없으면 harness가 안내하는 init 보완 절차로 그 줄만 채운다.
